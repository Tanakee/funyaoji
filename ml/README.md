# 強化学習

おじさんを強化学習で歩かせ、10m モードの理論値を出す。設計は [docs/ml.md](../docs/ml.md) にある。

物理演算は、ゲームと同じコード（`src/screen/game/sim.ts`）を Node で動かす。Python は、その Node のプロセスに行動を送り、観測と報酬を受け取る。

## 準備

- Node（リポジトリのルートで `npm install` を済ませる）
- [uv](https://docs.astral.sh/uv/)

```sh
cd ml
uv sync
```

## 動かし方

```sh
# ml/ で
# ① 決まった歩き方を CMA-ES で探す（1分ほど）。runs/<名前>/record_best.json に最良の歩き方と記録ができる
uv run python -m funyaoji_rl.openloop --seed 7

# ② PPO だけで学習する（2000 万ステップで約 30 分）
uv run python -m funyaoji_rl.train --reward r1 --gamma 0.99 --seed 0

# ③ ① の歩き方を土台に、AI が補正を足す
uv run python -m funyaoji_rl.train --reward r2 --gamma 0.99 --seed 0 \
  --base-gait runs/base-gait.json --log-std -1.5

# 最初の実験（③ の 12 run と ② の (R1)）を、決まった本数まで同時に流す
uv run python -m funyaoji_rl.sweep --parallel 8 --plan first

# 記録を並べて動画にする
uv run python -m funyaoji_rl.render --out runs/x/video runs/a/record_exact.json runs/b/record_exact.json

# MLflow の画面（http://127.0.0.1:5000）
uv run mlflow ui --backend-store-uri sqlite:///mlflow.db
```

| 残るもの | 内容 |
|---|---|
| パラメータ | 学習の設定、報酬（`reward`・`goal`・`k`）、`gamma`、乱数の種、土台の歩き方 |
| タグ | コミット、物理の指紋（`physics_fingerprint`）、Rapier の版、方法（`method`） |
| メトリクス | 学習の経過（`goal_rate`・`distance`・`goal_time`・`best_time`）、Stable-Baselines3 の損失や `train.explained_variance`、評価（`eval_exact_time`・`eval_time_median`・`eval_goal_rate`） |
| 成果物 | 50 万ステップごとの記録（`snapshots/`）、評価の記録（`records/`）、途中の走りを並べた動画（`video/progress.gif`・`progress.mp4`） |

## 最初の実験の結果

2026-11-28 に流した。体はゲームと同じ、物理の指紋は `50513d0d5e5e`（Rapier 0.21.0）。1本 2000 万ステップ。

- 「1回」は、そのままの重みで記録を再生したタイム
- 「中央値」は、出力の層の bias を少しずらして 16 回走らせた、ゴールした走りのタイムの中央値
- (E2) の判定（物理の不具合を突いていないか）は、まだ作っていない。だから、下のタイムは理論値の候補である

### 方法どうし

| 方法 | 1回 | 中央値 | ゴール率 |
|---|---|---|---|
| ① 決まった歩き方（CMA-ES） | 7.337 秒 | — | — |
| ② PPO だけ・(R2)・γ 0.99 | 歩き出さない（30 秒立ったまま、−0.52m） | — | 0% |
| ② PPO だけ・(R1)・γ 0.99 | 8.479 秒 | 8.459 秒 | 100% |
| ③ ① を土台に補正（12 run） | **6.813〜6.946 秒** | 6.813〜6.942 秒 | すべて 100% |

- ③ は ① より約 0.5 秒（7%）速い。体の状態を見て補正することに意味がある
- ② は報酬で結果が分かれた。(R2) は、ゴールしない走りの整形の割引和がどれも 0 になるので、一度もゴールしないうちは手がかりが弱い（docs/ml.md の「報酬」）。実際、2000 万ステップでも歩き出さなかった。でたらめに動かしても胴の補助で転ばず、30 秒立ったまま打ち切られる
- ③ は、学習の前（ほぼ土台のまま）から 10m に着くので、(R2) でも学習が進んだ

### ③ の報酬と γ（種 3 つの中央値）

| 報酬 | γ | 1回（中央値・最速〜最遅） | 中央値（中央値・最速〜最遅） |
|---|---|---|---|
| (R1) | 0.99 | 6.858（6.813〜6.871） | 6.867（6.813〜6.875） |
| (R1) | 0.995 | 6.879（6.875〜6.946） | 6.892（6.881〜6.942） |
| **(R2)** | **0.99** | **6.833（6.825〜6.858）** | **6.835（6.825〜6.869）** |
| (R2) | 0.995 | 6.883（6.850〜6.900） | 6.900（6.846〜6.911） |

- γ は、どちらの報酬でも 0.99 のほうが速い。γ = 0.99 は 1ステップ速いと価値が約 1% 増え、0.995 の約 0.5% より時間を詰める力が強い（docs/ml.md の「数値」）。予想どおり
- 報酬は、γ 0.99 で (R2) が少し速い。ただし差（約 0.03 秒）は種のぶれと同じくらいで、はっきりした差とは言えない
- いちばん速い1本は、(R1)・γ 0.99・種 0 の 6.813 秒
- ずらして 16 回走らせても、どの run もタイムの散らばりは 0.01〜0.02 秒で、どれも安定した走り
- 同じ設定・同じ種を2回流した run（(R1)・γ 0.995・種 2）は、タイムがすべて同じだった。同じ条件なら同じ結果になる

### ① の探す範囲

歩き方の値が探す範囲の端に張り付いたので、範囲を広げて流し直した（種を 3 つずつ）。

| 範囲（h0・A・K の上下） | 最速 |
|---|---|
| h0 0.05〜0.7、A 〜0.7、K 〜1.0 | 8.246 秒 |
| h0 0.05〜0.8、A 〜1.0、K 〜1.0 | 7.775 秒 |
| **h0 −0.5〜0.8、A 〜1.6、K 〜1.6** | **7.337 秒** |
| h0 −2.0〜1.0、A 〜5.0、K 〜5.0 | 7.383 秒 |

- 入力は 0〜1 で切られるので、範囲を広げるほど、もも とひざを端から端へ一気に切り替える動き（四角い波）に近づき、速くなった。一番広い範囲では、探す場所が広すぎて、かえって見つけにくくなった
- いまの既定は、太字の範囲

## 同時に流す本数

| 流し方 | 全体の速さ（ステップ/秒） |
|---|---|
| 1本だけ（Node 16 プロセス × 8 体） | 約 1.0〜1.1 万 |
| 1本だけ（Node 4 プロセス × 32 体） | 約 0.9 万 |
| 8本同時（1本あたり Node 4 プロセス × 32 体） | 約 1.7 万 |

- 8本同時でも CPU の使用率は 4 割ほどで、1本あたりは 4 倍以上遅くなる。8 本が同じ SQLite（`mlflow.db`）に書き込んで順番待ちになっている見込みだが、まだ確かめていない
