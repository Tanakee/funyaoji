# 強化学習（試作）

おじさんを強化学習（PPO）で歩かせ、10m モードの理論値を調べる。#68 の作業。

物理演算は、ゲームと同じコード（`src/screen/game/prototype/sim.ts`）を Node で動かす。Python は、その Node のプロセスに行動を送り、観測と報酬を受け取る。物理演算は CPU で動くので、GPU は要らない。

## 準備

- Node（リポジトリのルートで `npm install` を済ませる）
- [uv](https://docs.astral.sh/uv/)

```sh
cd ml
uv sync
```

## 学習から書き出しまで（1つのコマンド）

体の設定を変えたら、これを流し直す。

```sh
# ml/ で。探索で出した最速の歩き方を土台にして、AI がそこに補正を足す（今の champion の作り方。約 12 分）
uv run python -m funyaoji_rl.pipeline --steps 20000000 --name residual \
  --base-gait ../src/screen/game/prototype/lab/rl/body-b-fastest.json --log-std -1.5

# 土台なしで、AI が4つの関節の入力をそのまま決める
uv run python -m funyaoji_rl.pipeline --steps 20000000 --name free
```

土台の歩き方は、先に「比べる基準」の `openloop.ts` で作る。体の設定を変えたら、`openloop.ts` → `pipeline` の順に流し直す。`--base-gait` の候補の `params` が学習に使う体と違うときは、学習を始めずにエラーで止まる。

1. PPO で学習する。経過と重みが MLflow に残る。`runs/<名前>/<run の ID>/` にも同じものができる（同じ名前の学習を並べても、上書きし合わない）
2. 重みを評価する。そのままの重みで1回と、重みをほんの少しずらして 16 回走らせ、タイムの中央値を出す
3. そのままの重みで 10m に着いて不自然な動き（`lab/run.ts` の `sanity()`）が無く、ずらした 16 回のうち 15 回以上（`cleanRate >= 0.9`）もそうなら、MLflow のモデルのレジストリに登録する
4. 中央値が今の champion（`/prototype` で使う重み）より速ければ、champion を入れ替え、`src/screen/game/prototype/policy-b.json` に書き出す

書き出した `policy-b.json` は、コミットして PR に入れる。

```sh
# 報酬や打ち切りの設定を変える（src/screen/game/prototype/lab/rl/server.ts の EnvConfig）
uv run python -m funyaoji_rl.pipeline --name clean --config '{"wAir": -0.1, "maxJump": 0.25}'

# 学習だけ（評価も登録もしない）
uv run python -m funyaoji_rl.train --steps 2000000 --name try1

# 登録した重みの一覧 / champion を書き出し直す / 学習の済んだ run を評価して登録する
uv run python -m funyaoji_rl.registry list
uv run python -m funyaoji_rl.registry export
uv run python -m funyaoji_rl.registry submit <run の ID>
```

学習の間、更新のたびに1行ずつ出る。`goal_rate` は 10m に着いた割合、`best_time` は着いた中の最速、`best_clean` は不自然な動きに引っかからなかった中の最速。学習の間は行動に乱数を足しているので、乱数なしのタイムは評価で見る（そのままの重みの1回が `eval_exact_time`、重みをずらした 16 回の中央値が `eval_time`）。

評価で重みをずらすのは、1回のタイムがたまたまの値だから。同じ学習の重みでも、小数6桁に丸めただけで 8.67 秒が 13.54 秒になった（途中で1回つまずくかどうかが変わる）。16 回の中央値は 8.88 秒で、丸め方を変えてもほぼ動かない。`/prototype` で再生したときのタイムは、そのままの重みの1回（`eval_exact_time`）のほうになる。

## MLflow

MLflow は、オープンソースのものを手元で動かす。アカウントの登録も料金も要らない。記録は `ml/mlflow.db`（SQLite）と `ml/mlartifacts/` にでき、どちらもリポジトリには入れない。

```sh
# ml/ で。http://127.0.0.1:5000 で、実験の一覧・グラフ・登録した重みが見られる
uv run mlflow ui --backend-store-uri sqlite:///mlflow.db
```

| 残るもの | 内容 |
|---|---|
| パラメータ | 学習の設定（ステップ数・学習率など）と、環境の設定のうち既定から変えたもの（`env.` で始まる。体の設定 `env.params` は JSON の文字列） |
| タグ | コミット（`git_commit`、コミットしていない変更があったか `git_dirty`）、体の設定の指紋（`body`）、評価の結果（`eval_ended`・`eval_passed`） |
| メトリクス | 学習の経過（`goal_rate`・`distance`・`goal_time`・`best_time` など）と、評価（中央値 `eval_time`、最速 `eval_best`、最遅 `eval_worst`、きれいにゴールした割合 `eval_clean_rate`、そのままの重みの1回 `eval_exact_time` など） |
| 成果物 | 重み（`policy.json`）、経過（`history.json`）、学習に使った体の設定（`body-b.json`） |
| レジストリ | モデル `funyaoji-walker`。評価を通った重みが version として並ぶ。`champion` の別名が付いたものを `/prototype` で使う |

- 体の設定の指紋は、学習に使った体の値（`--config` の `params`、無ければ `body-b.json`。キーの順や数の書き方（`780` と `780.0`）には左右されない）と、物理と評価のコード（`sim.ts`・`policy.ts`・`bot.ts`・`lab/run.ts`・`lab/rl/play.ts`）から作る。指紋が違う重みどうしは、タイムを比べない。体を変えたあとの最初の登録は、速さにかかわらず champion になる
- `registry submit` は、run の指紋が今の指紋（今の `body-b.json` とコード）と違えば止める。評価は run に上げた `policy.json` で行う。`pipeline` は、`--config` の `params` が今の体と違えば、学習の前に止める
- 同じ run を `registry submit` し直しても、version は増えない（前に登録したものの結果を書き直す）
- `registry submit`（と `pipeline`）は、同時に2つ流さない。champion を読んでから付け替えるまでのあいだに、遅いほうが champion になることがある
- 別のマシンの MLflow に記録するときは、環境変数 `MLFLOW_TRACKING_URI` にその URL を入れる

## 再生

```sh
# リポジトリのルートで。Node で1回走らせ、タイムを出す
node src/screen/game/prototype/lab/rl/play.ts ml/runs/free/<run の ID>/policy.json

# 重みを少しずらして 16 回走らせ、中央値も出す（評価と同じ測り方）
node src/screen/game/prototype/lab/rl/play.ts ml/runs/free/<run の ID>/policy.json --trials 16

# ブラウザで見る：/prototype の「AI」を押す（policy-b.json の重みで動く）
```

重みは体の設定ごとに作る。体（`lab/rl/body-b.json` と `main.ts` の `BODIES`）を変えたら、学習し直す。

## 比べる基準（フィードバックなしの最速）

強化学習を使わずに、歩き方の機械（`bot.ts` の5つの値）だけで出せる最速のタイムを探す。AI がこれより速くなければ、深層を使う意味は薄い。

```sh
# リポジトリのルートで。乱数の種を変えて探し、最速の歩き方を候補の JSON に書く（種1つで30〜40秒）
node src/screen/game/prototype/lab/rl/openloop.ts --seeds 6 --out src/screen/game/prototype/lab/rl/body-b-fastest.json
```

`--out` のファイルがすでにあれば、その歩き方を今の体で測り直し、探した歩き方がそれより速いときだけ書く（`--force` で必ず書く）。書いたファイルは `vp fmt` の形にそろえるので、そのままコミットできる。

`/prototype` の「設定」で「お手本を、探索で出した最速の歩き方にする」を入れると、この歩き方をお手本として再生できる。

`body-b-fastest.json` は体 B の値の写しを持つ。体（`body-b.json` と `main.ts` の `BODIES`）を変えたら、上のコマンドで作り直す。

## 仕組み

| ファイル | 役割 |
|---|---|
| `src/screen/game/prototype/policy.ts` | 観測を作り、ニューラルネットを計算する。学習とブラウザで同じものを使う |
| `src/screen/game/prototype/lab/rl/server.ts` | 環境。おじさんを何体も持ち、標準入力の1行ごとに全員を1ステップ進める |
| `src/screen/game/prototype/lab/rl/bench.ts` | 環境が `lab/run.ts` と同じ結果になるかを確かめ、速さを測る |
| `src/screen/game/prototype/lab/rl/play.ts` | 重みを読み、1回走らせる |
| `src/screen/game/prototype/lab/rl/openloop.ts` | フィードバックなしの最速の歩き方を探す |
| `ml/funyaoji_rl/vec_env.py` | Node のプロセスを並べて、Stable-Baselines3 の環境にする |
| `ml/funyaoji_rl/train.py` | PPO で学習し、重みを JSON に書き出す。MLflow に記録する |
| `ml/funyaoji_rl/registry.py` | 重みを評価し、レジストリに登録する。champion を書き出す |
| `ml/funyaoji_rl/pipeline.py` | 学習・評価・登録・書き出しを続けて行う |
| `ml/funyaoji_rl/tracking.py` | MLflow の置き場所、コミット、体の設定の指紋 |

- AI の出力は4つ（-1〜1）で、毎秒30回（スマホの `tilt` と同じ）変える。`--config` の `actionHz` で変えたときは、その値を重みの JSON（`actionHz`）に書き、再生も同じ頻度にする。行動を変える間隔は、学習も再生も `round(240 / actionHz)` ステップ。`play.ts` は 1/60 秒（4ステップ）ごとにしか AI を呼ばないので、間隔が 4 の倍数になる値（60・30・20・15・12・10 など）だけを使える。ほかの値は学習の始めに止まる。土台なしなら、そのまま関節の入力（0〜1）に直す。土台ありなら、土台の歩き方の入力に、出力 × 補正の大きさ（`--residual-scale`、標準 0.3。重みの `base.scale`）を足す
- 観測は20個の数（胴の高さ・傾き・速度、関節の角度と回る速さ、足の接地、前の入力）。前後の位置は入れない。土台ありなら、歩き方の位相（sin, cos）の2つが増える
- 土台の歩き方と補正の大きさは、重みの JSON（`base`）に入る。再生する側は、JSON を読むだけでよい
- ニューラルネットは 64 個のユニットが2層。ブラウザでは `policy.ts` が計算するので、推論のサーバーは要らない

## 選んだものと、見送った案

太字が選んだもの。数字は、体 B・10m で測った値。

### 物理演算をどこで動かすか

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **ゲームと同じコード（`sim.ts`）を Node で動かす** | ゲームと同じ結果になる（お手本の歩き方で 13.892 秒が一致）。体を変えても、書き直しが要らない | Python と別のプロセスになり、つなぐ部分が要る。CPU でしか動かない |
| Python の物理エンジン（MuJoCo・Box2D）で作り直す | Python だけで完結し、既製の環境の形に乗れる | 別の物理になるので、出したタイムがゲームの理論値にならない。体を変えるたびに、2か所を直す |
| GPU で動く物理（MJX・Isaac）で作り直す | 何千体も同時に動かせて、GPU を使い切れる | 上と同じく別の物理になる。CPU でも 2000 万ステップが約 12 分で済むので、速さに困っていない |
| ヘッドレスのブラウザで動かす | 本番と同じ実行環境になる | 遅く、並列にしにくい。Node とブラウザで同じ結果になることは確かめた（8.671 秒が一致）ので、要らない |

### Python と Node のつなぎ方

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **Node のプロセスを並べ、標準入出力で JSON を1行ずつやり取りする** | 追加のライブラリもポートも要らない。プロセスの数だけ CPU のコアを使える（16 プロセスで毎秒約 2.7 万ステップ） | JSON の読み書きの分だけ遅い。1ステップごとに全プロセスの返事を待つ |
| HTTP・WebSocket のサーバーにする | 別のマシンの環境も使える | ポートの管理と、接続の後始末が要る。1台で足りているので、要らない |
| バイナリでやり取りする（共有メモリなど） | JSON より速い | 作る量が増え、中身を目で確かめにくい。今の速さで足りている |
| 学習も TypeScript で書く | プロセスが1つで済む | PPO を自分で書くことになる。MLflow などの道具も使いにくい |

### 学習の方法

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **探索で出した最速の歩き方を土台にして、PPO と小さいニューラルネットが補正を足す** | いちばん速く、走りが安定した（中央値 7.57 秒。少しずらした 16 回が 7.44〜7.70 秒に収まる）。学習の最初から 10m に着くので、報酬をいじらなくてよい | 先に探索が要る。土台の歩き方の近くしか探さないので、まったく別の走り方（跳ぶなど）は出てこない |
| PPO だけ（土台なし） | 並列の環境と相性がよく、設定をほとんど触らずに歩き出す（約 75 秒で 10m に着き始めた） | 遅く、走りが安定しない（中央値 8.88 秒。16 回が 8.69〜11.92 秒に散る）。報酬の決め方に敏感（下の「報酬」） |
| SAC・TD3 | 同じステップ数なら、PPO より賢くなりやすい | 1ステップあたりの計算が重い。環境が速いので、ステップ数を節約する意味が薄い |
| 歩き方の機械の値を探索する（深層なし） | 5つの値だけで、数分で 7.75 秒が出た（毎秒30回の入力に直すと 7.79 秒）。結果の意味が分かりやすい | 体の状態を見ないので、転びそうでも立て直せない。式で書ける歩き方しか出てこない |

深層を使う意味：土台の歩き方（毎秒30回で 7.79 秒）に対して、補正を足した AI は中央値 7.57 秒で、約 0.2 秒（3%）速い。歩くだけなら深層は要らず、5つの値の探索で理論値の 97% まで届く。残りの 3% を詰めるのに、深層が効いている。2000 万ステップの終わりでもまだ少しずつ速くなっていたので、長く学習すれば、もう少し縮む見込みがある。

補正の大きさ（入力の目盛りで ±0.3）と、学習の初めの乱数の大きさ（`--log-std -1.5`）は、最初に試した値のままで、比べていない。

### 報酬

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **前に進んだ距離 ＋ 弱い時間の減点（1秒で −0.5）＋ ゴール ＋5・転倒 −5** | 歩くところまでは安定して覚える | 時間の減点が弱く、速さを詰めきれない |
| 時間の減点を強くする（1秒で −3） | 速さを強く求められる | すぐ転んで減点を止めるほうが得になり、わざと転ぶ動きを覚えた（ゴール 0%） |
| 上に加えて、転倒したら残りの時間の分も減点する | わざと転ぶ得は無くなる | 転倒の減点が大きすぎて、立ったまま動かなくなった（ゴール 0%） |

土台の歩き方に補正を足す形にすると、最初から 10m に着くので、この弱い時間の減点のままで速くなった。報酬は変えていない。

### 行動を変える頻度

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **毎秒30回** | スマホの `tilt` と同じなので、人と同じ条件の理論値になる。学習のステップ数も半分で済む | 人には出せない細かさで動かせる点は残る（指の速さや反応の遅れは入れていない） |
| 毎秒60回（お手本の機械と同じ） | 今までの計測と同じ刻みになる | スマホより細かく動かせてしまう |
| 物理の刻みと同じ毎秒240回 | 物理が許す限界のタイムが出る | ゲームでは出せない操作になる。学習も遅い |

### 推論をどこで動かすか

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **重みを JSON にして、ブラウザの TypeScript で計算する（`policy.ts`）** | サーバーも追加のライブラリも要らない。会場の回線に左右されない。学習と同じコードで観測を作るので、ずれない | ニューラルネットの形を変えたら、`policy.ts` も直す。大きいモデルには向かない（今は約 6 千個の重みで、約 140KB） |
| ONNX にして、ONNX Runtime Web で動かす | どんな形のモデルでも動く | ライブラリが大きく、読み込みが遅くなる。この大きさのモデルには大げさ |
| 学習のマシンを推論のサーバーにする | モデルを差し替えやすい。GPU を使える | 会場から届く経路（VPN など）が要り、毎秒30回の往復の遅れも乗る。落ちるとデモが止まる |

### 重みをどこに置くか

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **`policy-b.json` をリポジトリに入れる** | プレビューでも本番でも、そのまま動く。どの重みで動いているかが PR で分かる | 学習し直すたびに差分が出る。JSON なので差分は読めない |
| ページを開いたときに、MLflow から取る | 差し替えにコミットが要らない | MLflow を外から見える場所に置く必要がある |
| R2 などの置き場所に上げる | リポジトリが太らない | 上げる手順と権限が増える。140KB なので、太る心配は小さい |

### 実験の記録

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **MLflow を手元で動かす（SQLite とフォルダ）** | 無料で、登録が要らない。サーバーを立てっぱなしにしなくても記録できる。レジストリも使える | 記録が1台の中にあり、ほかの人からは見えない |
| MLflow のサーバーを常に動かす（Docker など） | ほかのマシンからも記録・閲覧できる | 立てておく手間と、外から届く経路が要る。`MLFLOW_TRACKING_URI` を変えるだけで移れるので、必要になってからでよい |
| Databricks などのホスト版の MLflow | 自分で立てなくてよく、共有しやすい | アカウントの登録が要る。無料の枠に上限がある |
| Weights & Biases | グラフと共有が手軽 | アカウントの登録が要る。記録が外のサービスに出る |
| TensorBoard だけ | いちばん軽い | モデルのレジストリが無く、「どれを使うか」を管理できない |

### レジストリへの登録の形

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **`policy.json` を、そのままモデルの version にする** | ブラウザが読む形と同じファイルが、そのまま登録される。書き出しはコピーだけで済む | MLflow の「モデル」の形（pyfunc）ではないので、MLflow の配信の機能（`mlflow models serve`）は使えない |
| pyfunc のモデルとして登録する | MLflow の配信・評価の機能に乗れる | 推論はブラウザで行うので、使う場面が無い。Python の推論のコードを別に持つことになり、`policy.ts` とずれるおそれがある |

### 評価と、champion の決め方

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **そのままの重みで1回と、重みをほんの少しずらして 16 回走らせる。10m に着いて不自然な動きが無ければ登録。同じ体の中で、中央値がいちばん速いものを champion にする** | たまたまの1回に左右されない（丸め方を変えても、中央値は 8.8〜8.9 秒で動かない）。ゲームと同じコードで測る | 評価に 17 回走らせる（数秒）。`/prototype` で見えるタイムは、中央値ではなく、そのままの重みの1回になる。入力のずれや遅れへの強さは見ていない |
