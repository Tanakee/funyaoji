# 開発の進め方

## タスク

- タスクは GitHub の Issue で管理する
- Issue はテンプレート（タスク・不具合）に沿って書く

## ブランチ

- main に直接 push せず、ブランチを切って PR で入れる
- 名前は `<種類>/<短い英語>`。種類は下の「コミット」と同じ

例：`feat/tilt-input`、`fix/ragdoll-shake`、`chore/initial-setup`

## コミット

- 1つのコミットは1つの変更のまとまりにする。関係のない変更を混ぜない
- 何をしたかを、コミットメッセージの1行で言えないなら分ける
- どのコミットも、メッセージは `<種類>: <何をしたか（日本語）>` の形にする

| 種類 | 用途 |
|---|---|
| `feat` | 機能を足す・変える |
| `fix` | 不具合を直す |
| `docs` | ドキュメントだけを変える |
| `refactor` | 動きを変えずに書き直す |
| `chore` | 設定・環境・依存など、上のどれでもないもの |

例：`feat: スマホの傾きをサーバーに送る`

## プルリクエスト

- 1つの PR は1つの目的にする。関係のない変更を混ぜない
- タイトルはコミットメッセージと同じ形にする
- 本文はテンプレートに沿って書く。対応する Issue があれば `Closes #<Issue 番号>` を書く（マージで Issue が閉じる）
- 動かして確かめてから出す。画面が変わるなら、スクショか動画を付ける
- Squash and merge でマージする（マージしたブランチは自動で消える）。PR のタイトルが main のコミットメッセージに、PR の本文がその本文になるので、空の欄は消してからマージする
- PR を出すと GitHub Actions が次を確かめる。落ちていたら直してからマージする
  - PR の形：タイトルとブランチ名が上の形になっているか
  - CI：lint・型チェック・ビルドが通るか（`.github/workflows/ci.yml`）

## レビュー

PR は、動きが変わるかどうかで、レビューの承認（Approve）を待つかを分ける。

| マージの仕方 | 当てはまる変更 |
|---|---|
| 自分でマージしてよい | 動きが変わらない変更：ドキュメント、コメント、誤字、コードの整形、絵や素材の差し替え |
| 1人以上の Approve をもらってからマージする | 動きが変わる変更は全部 |

- 迷ったら Approve をもらう
- レビューを頼むときは、PR の Reviewers にチームの人を付ける。誰でもよいときは、全員を付ける
- 特定の人に見てほしいときは、PR のコメントでその人をメンションし、何を見てほしいかを書く
- 指摘を直したら、Reviewers の「再リクエスト」を押して、もう一度見てもらう

## ラベル

ラベルの一覧と意味は、GitHub のラベルの一覧（Issues → Labels）を見る。
