# 開発の進め方

## タスク

- タスクは GitHub の Issue で管理する
- Issue はテンプレート（親タスク・タスク・不具合）に沿って書く
- Issue は、必要だと思った人が作る

### 親の Issue と子の Issue

| 種類 | 内容 | テンプレート |
|---|---|---|
| 親の Issue | 動かして確かめられるまとまり。`type: parent` のラベルが付く | 親タスク |
| 子の Issue | 1つの PR で出せる大きさの作業。親の Issue に、sub-issue としてつなぐ | タスク |

- 親の Issue しか無いときは、着手する前に、必要な子の Issue を作る
- 仕様や方針に選択肢があり、選定が必要なときは、タスクとして Issue にする。`type: decision` のラベルを付け、決める人を Assignees に入れる。決めたことをドキュメントに反映したら閉じる
- 実装の中で決められることは、Issue にせず、PR の説明に書く

### 着手

- 着手するときに、自分を Assignees に入れる
- 先に終わらせる Issue があるときは、依存関係（blocked by）を付ける。「Blocked」の印が付いた Issue には着手しない
- 動きが変わらない小さな変更（誤字、コードの整形など）は、Issue を作らず、PR だけでよい

### ラベル

| ラベル | 付け方 |
|---|---|
| `area:` | 子の Issue に、関わる範囲を1つ以上付ける。親の Issue には付けない |
| `priority:` | すべての Issue に1つ付ける。企画書のスコープ（Must・Should・Could）に合わせる |
| `type:` | 当てはまるときだけ付ける。どれも付いていない Issue は、実装のタスク |

- ラベルの一覧と意味は、GitHub のラベルの一覧（Issues → Labels）を見る

## ブランチ

- main に直接 push せず、ブランチを切って PR で入れる
- 名前は `<種類>/<短い英語>`。種類は下の「コミット」と同じ

例：`feat/tilt-input`、`fix/ragdoll-shake`、`chore/initial-setup`

## コミット

- 1つのコミットは1つの変更のまとまりにする。関係のない変更を混ぜない
- 何をしたかを、コミットメッセージの1行で言えないなら分ける
- どのコミットも、メッセージは `<種類>: <何をしたか（日本語）>` の形にする

| 種類 | 用途 |
|---|---|
| `feat` | 機能を足す・変える |
| `fix` | 不具合を直す |
| `docs` | ドキュメントだけを変える |
| `refactor` | 動きを変えずに書き直す |
| `chore` | 設定・環境・依存など、上のどれでもないもの |

例：`feat: スマホの傾きをサーバーに送る`

## プルリクエスト

- 1つの PR は1つの目的にする。関係のない変更を混ぜない
- タイトルはコミットメッセージと同じ形にする
- 本文はテンプレートに沿って書く。対応する Issue があれば `Closes #<Issue 番号>` を書く（マージで Issue が閉じる）
- 動かして確かめてから出す。画面が変わるなら、スクショか動画を付ける
- Squash and merge でマージし、マージしたらブランチを消す。Squash and merge では、PR のタイトルが main のコミットメッセージになる

## レビュー

PR は、動きが変わるかどうかで、レビューの承認（Approve）を待つかを分ける。

| マージの仕方 | 当てはまる変更 |
|---|---|
| 自分でマージしてよい | 動きが変わらない変更：ドキュメント、コメント、誤字、コードの整形、絵や素材の差し替え |
| 1人以上の Approve をもらってからマージする | 動きが変わる変更は全部 |

- 迷ったら Approve をもらう
- レビューを頼むときは、PR の Reviewers にチームの人を付ける。誰でもよいときは、全員を付ける
- 特定の人に見てほしいときは、PR のコメントでその人をメンションし、何を見てほしいかを書く
- 指摘を直したら、Reviewers の「再リクエスト」を押して、もう一度見てもらう
