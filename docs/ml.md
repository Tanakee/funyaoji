# 強化学習

おじさんを強化学習で歩かせ、ノーマルモード（10m）の理論値を出す。企画書の Could「強化学習で、このゲームの理論値を調べる」にあたる。学習・記録・CI の学習し直しは、[モードの一覧](#モードの一覧)から回るので、ほかのモードもその一覧に足せば理論値を出せる。

試作（`src/screen/game/prototype/`、main には入れていない）の上で一度作ったが、本番の物理（`src/screen/game/sim.ts`）の上で作り直す。試作で分かったことは、各項の「試作で分かったこと」に残す。

太字が選んだもの。

## 目的

| 目的 | 扱い |
|---|---|
| (a) 理論値を出す。人のチームのタイムと比べる物差しにする | やる |
| (b) 発表やデモで、AI が走る姿を見せる | やる。どこで見せるかは、企画書とゲームの進行に仕様を足してから決める |
| (c) 4人そろわなくても、足りない関節を AI が動かして遊べる | できたらやる。妨げない設計にしておく |
| (d) 体の設定を変えたときに、歩けるかを確かめる道具 | やらない |

- (a) と (b) は、AI が出した入力（毎秒30回の4つの値）を記録して再生すれば足りる。物理は乱数を使わないので、同じ入力なら同じ走りになる。ゲームの中で AI を計算するのは (c) だけ
- (d) をやらないので、体を変えるたびに学習し直す仕組みは作らない

## 理論値の定義

理論値は「毎秒30回・4つの関節を同時に切り替える条件で、ゲームの入力で出せる最速のタイム」とする。報告するときは、いつもこの条件を添える。

| 案 | AI に許すこと | 良い点 | 悪い点 |
|---|---|---|---|
| **(i) 毎秒30回・4つ同時の切り替えの限界** | 毎秒30回、4つの関節を同時に、0〜1 のどの値にも一瞬で変えられる。遅れは無い | 定義がはっきりしていて、測る値が要らない。スマホの `tilt` と同じ回数なので、学習の刻みにそのまま使える | 人には届かない。関節が震えるような動きを覚えやすい。ゲームが受け付けるすべての入力の限界ではない（下の注） |
| (ii) 人の手の限界を入れる | (i) に加えて、1回の変化の大きさと、通信の遅れを制限する | 人が完璧に動かしたときの最速になり、人のタイムと比べやすい | 変化の大きさの上限を、スマホの `tilt` を記録して測る必要がある。遅れがあると、見えている状態だけでは次が決まらず、学習が難しくなる |

- (i) は「ゲームが許す限界」ではない。ゲームは描画のフレームごとに入力を読み、関節ごとの傾きは、それぞれのスマホから別々の時刻に届く。キーボードには、それとは別の速さの上限がある。だから、毎秒30回より細かい切り替えや、関節ごとにずらした切り替えも、ゲームには入りうる。(i) はその中で「毎秒30回・4つ同時」に絞った上での最速である。名前は理論値のままにし、条件を添えて言う
- (ii) と (c) のエージェントも、あとで作れるようにする。人らしさ（変化の制限・遅れ・ノイズ・AI が動かす関節）は、環境の設定として付け外しする（Gymnasium のラッパーの考え方）。物理・報酬・終わり方は、どのエージェントでも同じものを使う。観測は同じものを土台にするが、次の2つは違う
  - 遅れを入れる (ii) と (c) では、まだ物理に届いていない過去の行動を観測に足す。遅れがあると、いまの状態だけでは次が決まらないため
  - ③（[決まった歩き方を土台にするか](#決まった歩き方を土台にするか)）の歩き方の位相は、決まった時計に合わせて動く前提で、(c) には合わない。人は決まった時計で動かないので、(c) は土台を使わない ② の形の上に作る

| エージェント | 設定 |
|---|---|
| (i) 理論値 | 全部なし |
| (ii) 人の限界 | 変化の制限＋遅れ |
| (c) 人と組む | 遅れ＋ノイズ＋AI が動かす関節を一部にする |

- 人らしさの3つは別のもの。変化の制限と遅れは乱数ではなく、(ii) に要る。ノイズは乱数で、乱れても転ばない強さのために (c) に要る
- 作る順番は (i) を先にする。(ii) は測った値が無いと意味が弱く、遅れを入れると問題が一段難しくなるので、(i) で全体を通してから入れる

## 問題の定義

### 行動

4つの関節の入力（0〜1）。毎秒30回（スマホの `tilt` と同じ）変える。1回の行動で、物理を 1/240 秒ずつ、最大 8 ステップ進める。走りが終わったら（ゴール・転倒・座り込み）、そこで止まる。

- 行動は、物理に渡す前に Node の側で 1/1000 の目盛りにそろえる（[入力の記録の置き場所](#入力の記録の置き場所)）

### 観測

AI（actor）は 22 個を見る。学習の間に価値を見積もる側（critic）は、その 22 個に、上限を切らないゴールまでの残りを1つ足した 23 個を見る（非対称の actor-critic。actor と critic で見るものを変える形）。

| 観測 | 数 |
|---|---|
| 胴の高さ（立った姿勢からの差）、傾き（sin・cos）、前後と上下の速度、回る速さ | 6 |
| 関節の角度。行動と同じ目盛り（範囲の両端を 0 と 1） | 4 |
| 関節の回る速さ | 4 |
| 足の接地（右・左） | 2 |
| 前の行動。実際に物理に渡した値（1/1000 にそろえたあと。③ では土台と補正を足し、0〜1 に収めてそろえたあと） | 4 |
| 座り込みの時計（胴の中心が 1.0m より低くなってからの秒数 ÷ 3秒。低くなければ 0） | 1 |
| ゴールまでの残り（`min(10 − x, 1.5) / 1.5`） | 1 |
| critic だけ：ゴールまでの残り。上限を切らない（`(10 − x) / 10`） | 1 |

決まった歩き方を土台にする学習（[学習の方法](#学習の方法)）では、歩き方の位相（sin・cos）の2つが増えて、actor は 24 個、critic は 25 個になる。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| (A) 物理の状態を全部（5つの部位の位置・角度・速度・回る速さ） | 物理の状態をすべて見せるので、この先の動きが決まる | 前後の位置まで入れると、場所で動きを覚えてしまう |
| **(B) 歩くのに要るものに絞る** | (A) とほぼ同じ情報。おじさんは胴から脚がつながった鎖なので、胴と関節から全部の部位がほぼ計算で出る（下の注）。関節の角度が行動と同じ目盛りなので、狙った角度とのずれがすぐ分かる。脚のロボットの研究や Gymnasium の BipedalWalker と同じ形。試作でこの形で 10m を歩いた | 何を捨てるかを人が決めている |
| (C) 画面の絵 | 人と同じ情報になる | 学習がとても重くなり、この目的には大げさ |

- 考え方の軸はマルコフ性（いま見えているものだけで、この先の動きが決まるか）。決まらないと、同じ見た目の状態で違う結果を見せられ、学習が迷う
- (B) は、厳密にはマルコフではなく、近い形である。部位は別々の剛体で、柔らかい関節（impulse joint。ずれを力で引き戻すつなぎ方）でつながっているので、関節はわずかにずれる。胴と関節の角度から全部の部位を出すのは近似になる。ずれは小さいので、これで足りるとする
- 座り込みの時計は必須。本番の物理には「胴の中心が 1.0m より低い状態が 3秒続いたら終わる」決まりがあり、低くなってからの時間が見えないと、もうすぐ終わる状態とまだ余裕のある状態を区別できない。試作の物理にはこの決まりが無かった
- ゴールまでの残りは、1.5m で上限を切って actor に見せる。本番の物理は、同じステップの中でゴールを転倒より先に判定するので、胴の中心が 10m を越えた瞬間に倒れていてもゴールになる。最後に前へ倒れ込めば縮む見込みがあり、理論値ではこれも取りにいく。遠いあいだは値が変わらないので、場所に依存せずに歩ける

critic に見せるもの。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| actor と同じ 22 個 | 書き足しが要らない | (R2) の報酬では、価値が x で大きく変わるのに、0〜8.5m のあいだは残りが同じ値になり、critic が見分けられない |
| **actor の観測に、上限を切らない残りを足す** | critic が価値を正しく見積もれる。actor は場所を見ないままなので、場所で動きを覚えない | Stable-Baselines3 に小さな方策を書き足す。観測を分け、actor は足した1つを使わない |
| actor にも上限を切らない残りを見せる | 書き足しが要らない | actor が場所で動きを覚えてしまう |

- (R2)（[報酬](#報酬)）の価値は、おおよそ G・γ^(残りのステップ数) − k・x になり、x で大きく変わる。10m を 225 ステップ（約 1.3 m/秒）で歩く方策で γ = 0.99 なら、G = 10 のとき、x = 0 で約 +1.0、x = 5 で約 −1.8、x = 8.4 で約 −1.4。G = 30 なら約 +3.1、+4.7、+12.5。上限を切った残りでは、このどれもが同じ観測に見える
- 前は「前後の位置を critic にだけ見せる」案を、「critic がゴール直前の倒れ込みを評価できても、actor は位置を見ないので動きを変えられない」として見送った。これは actor の話で、critic の見積もりの正しさを見落としていた。critic の見積もりがずれると、actor に渡る「この行動はどれだけ良かったか」の値もずれる
- 経過時間は見せない。学習の上限時間を「打ち切り」として扱えば要らない（[終わり方](#終わり方)）

### 報酬

**ゴールしたら +G。それに、ポテンシャル型の整形 F = γ・Φ(次の状態) − Φ(今の状態)、Φ = k・x（胴の前後の位置）を毎ステップ足す。** 終わった状態（ゴール・転倒）の Φ は 0 として扱う。打ち切りでは 0 にしない。整形の γ は、PPO の γ と同じ値にする。最初は k = 1（1m で 1）、G = 30。

| 案 | 報酬 | 良い点 | 悪い点 |
|---|---|---|---|
| (R1) 試作の形 | 前に進んだ距離 ＋ 時間の減点 ＋ ゴール ＋5・転倒 −5 | 試作で歩いた | 決める値が4つあり、どれも根拠を説明しにくい。時間の減点を歩く速さより強くすると、わざと転ぶ |
| **(R2) 本当の目的 ＋ ポテンシャル型の整形** | 上のとおり | 割引のある目的のもとで、整形がどの方策がいちばん良いかを変えないことが、理論で保証される（Ng ら 1999）。わざと転ぶ抜け道が無い。決める値は G と k の2つ | 試作と違う形なので、同じように学習が進むかは試すまで分からない。一度もゴールしないうちは、手がかりが理屈の上では弱い（下の注） |

- 欲しいのは「ゴールまでの時間を最短にする」ことだけ。ゴールに +G だけを与えると、T ステップでのゴールの価値は G × γ^T で、速いほど大きい。転倒は 0 で、必ずゴールより悪い。ただ、最初の AI はすぐ転んで一度もゴールしないので、これだけでは学習が始まらない。そこで前進を道しるべとして足す
- ポテンシャル型の整形は、1回分を全部足すと途中が打ち消し合うので、どの方策がいちばん良いかを変えない。転倒すると、それまでの前進でもらった分（k・x）がまとめて引かれるので、転倒の減点を別に決めなくてよい
- 整形の γ と PPO の γ が違うと、打ち消し合わなくなり、この保証が崩れる
- Ng らの保証は「割引のある目的での方策の順位」についてのもの。(R2) が最大にするのは、ゴールの見込みと速さを合わせた G・γ^T の期待値（転倒は 0）である。ゴール率や、ゴールしたときの平均タイムで並べた順位とは、違うことがある。たとえば γ = 0.99 で、90% が 225 ステップでゴールする方策（0.9 × 0.104 ≈ 0.094）は、100% が 240 ステップでゴールする方策（0.090）より良いとされる。だから (R1) と (R2) を比べるときは、ゴール率も見る
- k は「途中の手がかりの濃さ」で、割引のある目的での方策の順位は変えない。大きいと 1ステップごとの報酬のぶれにゴールの価値が埋もれ、小さいと手がかりが薄くて学習が遅い。学習の進み方が変わるので、結果として出る成績は k で変わりうる
- スタートは x = 0 で、終わった状態の Φ は 0 なので、ゴールせずに終わった走り（転倒・座り込み）は、整形を割引して全部足すと 0 になる。前に進んでから転んでも、すぐ転んでも同じになる。だから一度もゴールしないうちは、手がかりは理屈の上では弱い。実際には、critic の見積もりの近似と GAE（数ステップ先までの報酬と critic の見積もりを混ぜて、行動の良さを出す方法）を通して、前進が手がかりになる。② は土台が無く、ゴールまでたどり着かずに止まるおそれがある。③ は土台の歩き方で最初からゴールするので、この心配は小さい
- ゴールしたステップの報酬は G − k・x（終わった状態の Φ は 0 なので、それまでの前進の分がここで引かれる）。G = 10・k = 1 なら、x ≈ 10 で G − k・x ≈ 0 となり、ゴールしたこと自体がほとんど報酬に出ない。だから G は k・10 よりずっと大きくする。最初は k = 1・G = 30 にする（ゴールのステップで約 +20）

試作で分かったこと。

- 時間の減点を 1秒で −3 にすると、わざと転ぶ動きを覚えた（ゴール 0%）。10m を 7.6 秒で歩くと速さは約 1.3 m/秒で、歩いていても毎秒 −1.7 になり、続けるほど損だったため。1秒で −0.5 なら、歩けば毎秒 +0.8 で、歩き続けた
- 転倒したら残りの時間の分も減点すると、立ったまま動かなくなった（ゴール 0%）

### 終わり方

| 終わり方 | 扱い |
|---|---|
| ゴール・転倒・座り込み | 本番の物理の判定をそのまま使う。終わった（terminated）として返す |
| 学習の上限時間（たとえば 30 秒） | 打ち切った（truncated）として返す |

- ゲームには制限時間が無い（[ゲームの進行](game.md)）。上限時間は、止まったまま終わらないと困る学習の都合なので、ゲームのルールとは分ける
- 打ち切りなら、Stable-Baselines3 は「この先もまだ続いた」として critic の見積もりで価値を補う。終わったとして返すと、時間切れを罰のように覚えてしまう
- ゴール・転倒と上限時間が同じステップで起きたら、ゲームの終わりを優先する。終わった（terminated）として返し、Φ は 0 にする
- 1つのプロセスにおじさんを何体も持たせるので（[Python と物理をつなぐ](#python-と物理をつなぐ)）、Stable-Baselines3 の VecEnv（並べた環境をまとめて動かす入れ物）を自分で書く。Stable-Baselines3 の決まりに合わせ、次の2つを info に入れる
  - `info["TimeLimit.truncated"] = truncated and not terminated`。これが無いと、打ち切りが終わりとして扱われる
  - `info["terminal_observation"]` に、やり直す前の最後の観測（critic の分を含む）。VecEnv は終わったらすぐやり直すので、返す観測は次の走りの最初になっている。打ち切りで価値を補うのに、この最後の観測を使う

## 物理とのつなぎ方

### Python と物理をつなぐ

**本番の `sim.ts` を Node で動かす。Node のプロセスを並べ、標準入出力で JSON を1行ずつやり取りする。** 1つのプロセスにおじさんを何体も持たせ、プロセスを CPU のコアの数だけ並べる。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **Node のプロセスを並べ、標準入出力で JSON** | ゲームと同じ物理になる。追加のライブラリもポートも要らない。試作で毎秒約 2.7 万ステップ出た | JSON の読み書きの分だけ遅い |
| 物理を Python で作り直す（MuJoCo・Box2D） | Python だけで完結する | ゲームと別の物理になり、理論値にならない |
| HTTP や共有メモリでつなぐ | 速くできる | 作る量が増える。今の速さで困っていない |

### 観測に要る値を読む

**本番の `Sim` に、読むだけのメソッドを1つ足す。** 観測に要る値を、ただの数で返す。物理エンジンの型は外に出さない。観測の式は強化学習の側に置く。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **`Sim` に読むだけのメソッドを足す** | ゲームの動きは変わらない。物理エンジンの型が外に出ない。テストで守れる | 本番のコードを少し変える |
| 強化学習の側から、`Sim` の中身（private）に手を入れる | 本番のコードを変えない | `sim.ts` が変わると黙って壊れる |
| `state()` の位置の差から速度を出す | 本番のコードを変えない | 不正確で、1ステップ遅れる。足の接地も計算し直す |

- `Sim` は今、`state()` で各部位の位置と傾きしか読めない
- メソッドが返すもの
  - 部位ごとの速度と回る速さ
  - 関節の角度と回る速さ。角度は、関節の範囲（`body.ts` の `range`）の向きのまま返す。ひざの範囲は `[0, −1.649]` で、数が小さいほど曲がっている。0〜1 の目盛りにするときは、`range[0]` を 0、`range[1]` を 1 として、そのまま割る（大きい方・小さい方に並べ替えない）
  - 角度は ±π で折り返すので、部位の傾きの差から関節の角度を出すときは、折り返しを直す
  - 足の接地（右・左）。足はすねの部位の中の形の1つなので、足の形と地面の接触を見るか、すねの姿勢と足の形から計算して出す
  - 座り込みの時計。低くなった時刻（`sittingSinceMs`）は今 private なので、低くなってからの秒数として返す

### 刻みを変えられるようにする

**`Sim` に物理の刻みの引数を足す。既定は `STEP_S`（1/240 秒）で、ゲームは変わらない。** 刻みは、物理エンジンの刻み（`world.timestep`）、胴を起こす補助（`assistTorso()`）の式、`advance()` のステップの数え方、経過時間のすべてに使う。[数えない走り](#数えない走り)の参考の数字（刻みを細かくして走らせ直す）に使う。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **`Sim` に刻みの引数を足す** | `Sim` ごとに変えられる。ゲームは既定のまま | 本番のコードを少し変える |
| `body.ts` の `STEP_S` を書き換えて動かす | 本番のコードを変えない | モジュールの定数なので、同じプロセスで比べられない。書き換え忘れるとゲームが変わる |
| `world.timestep` だけ変える | 変える所が1つ | 補助の式と経過時間が 1/240 秒のままで、別の物理になる |

### 置き場所

| 置き場所 | 置くもの |
|---|---|
| `src/screen/game/ai/` | 観測の計算・再生など、ゲームでも使うもの。DOM にも Node にも依存しない |
| `scripts/rl/` | 学習の環境のサーバー・ベンチマークなど、Node でだけ使う道具 |
| `ml/` | 学習の Python |

- 観測の計算は、(c) でゲームの中で AI を動かすときにも同じものを使う

### モードの一覧

**モードごとの設定（今は `Sim` の設定だけ）を、`src/screen/game/modes.ts` の `MODE_SETTINGS` の1か所に置く。** 強化学習の道具（学習の環境・物理の指紋・理論値の記録・再生の一致のテスト・CI の学習し直し）は、どれもこの一覧を回り、一覧から `Sim` を作る。モードを1つ足すと、CI がそのモードの記録を作り、差し替える PR を出す（[物理の変更から記録の差し替えまでを自動にする](#物理の変更から記録の差し替えまでを自動にする)）。

- キーはゲームのモード（`src/shared/messages.ts` の `MODES`）と同じ値にする。学習の道具の引数（`--mode normal`）、記録のファイル名、MLflow のタグにも、この値をそのまま使う
- 値はモードの設定（`ModeSettings`）で、今は `Sim` の設定（`sim`）だけを持つ。`sim` は、`SimOptions` からモードで変わらないもの（物理の刻み `stepS`・練習 `practice`）を除いた形（`ModeSimOptions`）。ハードの `hard: true` や、障害物の設定を載せられる
- `sim` で包んでおくのは、障害物モードなどで、観測の形・学習の設定・土台の歩き方をモードごとに足せるようにするため
- まだ物理の無いモードは載せない。今はノーマル（`{ sim: {} }`）とハード（`{ sim: { hard: true } }`）を載せている
- ゲーム（`src/screen/game/game.ts`）も、この一覧から `Sim` を作る（`modeSimOptions()`。練習は、それに `practice: true` を足す）。ゲームのモード（`MODES`）が一覧にそろっていないと、型のチェックで落ちる
- 学習の道具の Node のプロセス（`scripts/rl/server.ts`）は、1つのモードだけを扱う。モードは立てるときに `--mode` で渡し、省くとノーマルになる
- 物理の指紋にモードの名前は入れない。物理が同じなら、モードが違っても同じ指紋になる

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **`src/screen/game/modes.ts` に、ゲームのモードの値をキーにして置く** | ゲームと学習が同じ一覧から `Sim` を作れる。`Mode` の型で、ゲームに無いモードを書けない | 物理の無いモードを載せないので、ゲームの `MODES` と一致しない間がある |
| `scripts/rl/` に、学習だけの一覧を置く | ゲームのコードを変えない | ゲームと学習で、モードの物理の設定が別々になり、ずれうる |
| `src/shared/messages.ts` の `MODES` に設定を持たせる | 一覧が1つで済む | 通信の仕様のファイルに、物理（画面だけで使う）の設定が入る |

- (c) や障害物モードで、モードによって観測の形が変わるときは、観測の形もモードごとに持つ必要がある。まだ作っていない。足すときは、モードの設定（`ModeSettings`）に足す

### 再生をそろえる

AI の入力を画面で再生するときは、画面の時間を溜め、1/30 秒たまるごとに `advance(記録[k], 1/30)` を1回呼ぶ。記録の1つが物理の 8 ステップ（終わる回だけは 8 以下）に対応し、学習と同じ走りになる。

- ゲームの画面は、フレームごと（ぶれる）に入力を読むので、普段の進め方のままでは入力が切り替わる物理のステップがずれる。物理は少しのずれで結果が大きく変わる（試作では、重みを丸めただけで 8.67 秒が 13.54 秒になった）
- `advance(入力, 1/30)` は、最大 8 ステップ進む。走りが終わったら（ゴール・転倒・座り込み）、そこで止まる。途中では毎回 8 ステップで（試作で 300 回試して全部 8）、最後の1回だけ少ないことがある（デモの歩き方では、最後の呼び出しが 7 ステップで終わった）。だからタイムは記録の長さ × 1/30 秒から出さず、いつも `Sim` から読む
- `game.ts` は今、フレームごとに `advance(入力, dt)` を1回呼ぶだけなので、再生の道を足す。画面の時間を溜め、1/30 秒ごとに記録を1つ進めて `advance(記録[k], 1/30)` を呼ぶ。1フレームに 1/30 秒が何回分もたまったら、その回数だけ呼ぶ。今の `MAX_FRAME_S`（1フレームで進める上限）は、溜める前にかける。タブが裏に回ったときなどは再生が遅れるが、物理のステップと入力の対応はずれない

### Node とブラウザの一致

**一度確かめて終わりにせず、守るものとして扱う。** 学習と記録は Node、見せるのはブラウザなので、同じ入力で同じタイムにならないと、記録が画面で再現しない。試作の物理では一致した（8.671 秒）が、保証されてはいない。

- `touchesGround()` は JavaScript の `Math.sin`・`Math.cos` を使う。この結果の最後の桁は、JavaScript のエンジン（Chrome・Firefox・Safari）で違いうる
- 普段の `@dimforge/rapier2d-compat` は、違う環境で同じ結果になることを保証していない。Rapier には、環境が違っても同じ結果になるように作った版（決定的な版）がある
- 進め方
  - 早めに、見せる先のブラウザ（会場の PC のブラウザ）で、Node と同じタイムになるかを確かめる。2026-11-28 に Chromium 152 で確かめ、理論値の記録とお手本の歩き方のどちらも、タイムと最後の胴の位置が最後の桁まで一致した。Firefox と Safari はまだ
  - 合わなければ、Rapier の決定的な版に替えることを考える。ゲームの物理も替わるので、速さとの引き換えになる
  - あとで、ブラウザで記録を再生するテストを足すことを考える

## 学習の方法

### アルゴリズム

**PPO（Stable-Baselines3）。**

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **PPO** | 並べた環境から一度にたくさん集めて学ぶので、速い環境と相性がよい。設定に鈍く、扱いやすい | 集めたデータを使い捨てるので、多くのステップが要る |
| SAC・TD3 | データを使い回すので、少ないステップで賢くなる | 1ステップあたりの計算が重い。環境が速いので、ステップを節約する意味が薄い |

### 決まった歩き方を土台にするか

**① → ③ の順に作り、② も比べる。いちばん速いものを理論値として報告する。**

| 方法 | 中身 | 試作の結果（体 B・10m） |
|---|---|---|
| ① 探索だけ（機械学習なし） | 歩き方の機械の値（5つ）を CMA-ES で探す。体の状態は見ない | 7.79 秒（CMA-ES ではなく簡単な探索。毎秒60回の入力で探し、毎秒30回の入力で測り直した値） |
| ② PPO だけ | AI が4つの関節を直接決める | 中央値 8.88 秒（16 回が 8.69〜11.92 秒に散る） |
| ③ ① を土台に、PPO が補正を足す | 土台の入力に、AI の出力 × 0.3 を足す | 中央値 7.57 秒（16 回が 7.44〜7.70 秒） |

- 理論値は、どの方法で出しても「本当の最速の上限」でしかない。7.5 秒が出たら「最速は 7.5 秒以下」と言えるだけなので、方法を1つに絞らず、いちばん速いものを報告する
- ③ には ① が要る。① は「深層を使う意味があるか」の物差しにもなる
- ③ は土台の近くしか探さないので、② がまったく別の走り方でもっと速くなる見込みは残る
- 試作の ① は、CMA-ES ではない。上位の候補の平均をとり、ばらつきを縮めていくだけの簡単な探索で、値どうしの関係（共分散）は合わせていない。毎秒60回の入力で探した。本番の ① は、本当の CMA-ES を、②③ と同じ環境（毎秒30回・1/1000 の目盛り）で回す
- ③ では、補正が 0 のとき、① とまったく同じ入力・同じタイムになることを確かめる（テストに入れる）。土台の位相や目盛りのそろえ方がずれていると、③ が ① から始まらない
- ① の探す範囲は、値が範囲の端に張り付いたら広げる。入力は 0〜1 で切られるので、ももの中心（h0）を 0 より下、振れ幅（A）とひざの曲げ（K）を 1 より上まで探すと、端から端へ一気に切り替える動き（四角い波）に近い歩き方も探せる。最初の実験では、h0 −0.5〜0.8、A・K 〜1.6 がいちばん速かった（ml/README.md）

### 数値

| 値 | 最初の値 | 考え方 |
|---|---|---|
| G（ゴール） | 30 | [報酬](#報酬)。ゴールのステップの報酬 G − k・x が 0 に近くならないよう、k・10 よりずっと大きくする |
| k（道しるべ） | 1 | [報酬](#報酬) |
| γ（割引率） | 0.99（最初の実験で 0.995 と比べ、どちらの報酬でも 0.99 が速かった） | 10m は約 7.5 秒 ＝ 225 ステップ。γ = 0.99 なら γ^225 ≈ 0.10 で、1ステップ速いと価値が約 1% 増え、時間を詰める力が強い。代わりに遠い先が見えにくい。0.995 なら γ^225 ≈ 0.32 で、1ステップ速いと約 0.5% 増える。0.999 なら γ^225 ≈ 0.80 で先まで見えるが、1ステップで約 0.1% しか増えない |

最初の実験は、報酬の (R1) と (R2)、γ の 0.99 と 0.995 の比べ合いにする。③ で流し、② は (R1) と (R2) を1本ずつ流す（[比べ方](#比べ方)）。

## 評価

### 理論値として出す数字

| 数字 | 意味 | 使い道 |
|---|---|---|
| **記録した入力を再生したタイム（1回）** | 「この入力を入れれば、このタイムが出る」という事実。誰でも再生して確かめられる | 理論値として報告する。(b) で見せる。別名の入れ替えで比べる |
| **少しずらして走らせたときの、ゴール率とタイムの中央値** | AI が、たまたま速いのか、安定して速いのか | 学習の結果どうしを比べる。(c) の強さの目安にする |

- 理論値は「この条件でゲームの入力で出せる最速」なので、たまたまでも、その入力で出せたなら正当な記録になる
- 学習の設定（報酬・γ など）の良し悪しは、たまたまの1回では見誤る。試作では、重みを小数6桁に丸めただけで 8.67 秒が 13.54 秒になった（途中で1回つまずくかが変わる）。16 回の中央値は 8.88 秒で、丸め方を変えてもほぼ動かなかった
- 言葉の決まり
  - ゴール率は、ゴールした回数 ÷ 走らせた回数。転倒・座り込み・打ち切りは、ゴールしなかった回に数える
  - タイムは、ゴールした走りの `Sim` のタイム（成功したときのタイム）
- ずらし方
  - ②③ は重みを少しずらす。① は重みが無いので、歩き方の機械の値を少しずらす
  - ずらしは、入力が 1/1000 の目盛りより大きく変わる大きさにする。小さいと、丸めで消えて同じ入力になる。たとえば ③ では AI の出力が 0.3 倍されるので、出力のずれが 0.001 でも入力では 0.0003 になり、目盛りの半分（0.0005）より小さく、丸めで消える。ずらしたあと、入力が実際に変わったことを確かめる

ずらした走りのまとめ方。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **ゴール率と、ゴールした走りだけのタイムの中央値を、いつも並べて出す** | 「どれだけゴールするか」と「ゴールしたらどれだけ速いか」が分かれて読める | 2つの数を見て比べる必要がある |
| 転んだ走りを限りなく遅いタイムとして、全体の中央値をとる | 1つの数で比べられる | ゴール率が半分を切ると中央値が決まらず、差が見えない。ゴール率の差とタイムの差が混ざる |
| ゴールした走りだけの中央値（ゴール率を出さない） | 簡単 | 転びやすい設定ほど、たまたま速い走りだけが残り、良く見える |

PPO（②③）から記録を作るときの候補。

- 候補は2種類。行動の乱数を使わない走り（AI が出す平均の行動）の1回と、ずらして走らせた中で最速の走り
- (E1) と (E2)（[数えない走り](#数えない走り)）の候補は、別々に持つ。最速の走りが (E2) を通らなくても、(E2) を通った中の最速が失われないようにする

### 数えない走り

**理論値は (E1) と (E2) を両方出し、(E2) を見出しにする。** (b) で見せるのも (E2) の記録にする。

| 案 | 数えないもの | 良い点 | 悪い点 |
|---|---|---|---|
| (E1) 何でもあり | なし | 定義どおり、ゲームで起きることは全部ゲームとして数える。判定が要らない | 物理の不具合を突いた走りが理論値になりうる |
| **(E2) 物理の不具合だけ除く** | エネルギーが湧いて跳ね上がる、地面にめり込む、関節が範囲を突き抜ける | 走る・跳ねるは認め、ゲームの意図に沿った最速になる | 判定を作る必要がある |
| (E3) 試作と同じ（`sanity()`） | 上に加え、平均 2.5 m/秒・最大 5 m/秒より速い、胴が 25cm 跳ね上がる、両足が浮く時間が 30% を超える | 試作の判定がそのまま使える | 走る・跳ねるまで除くので、理論値が遅くなる。しきい値の根拠が弱い |

- 試作の判定には、物理の不具合と、歩き方の好み（走る・跳ねる）が混ざっていた。理論値は、この条件でゲームの入力で出せる最速なので、走る・跳ねるは除かない
- (E1) と (E2) の差が大きければ、物理に穴があるという発見になり、ゲームの直すところが分かる

(E2) の判定のしかた。

**直接測れるおかしさだけで除く。** 測るのは、関節が範囲を越えた量（rad）、地面へのめり込みの深さ（m）、跳ね上がり・ありえない速さ。それぞれに、許す量と、それが続いた時間を決め、両方を越えたら除く。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **直接測れるおかしさだけで除く** | 何を除いたかがはっきりしていて、説明できる | しきい値を決める必要がある |
| 物理の刻みを細かくして（1/240 秒 → 1/480 秒）、記録を再生し直し、崩れたら除く（前の案） | 刻みの粗さが生んだ不具合を、まとめて拾えそうに見える | 正しく働かない。記録は、状態を見て入力を決める方策（閉じたループ）が出した入力の列である。刻みを変えると状態がずれるのに、記録の入力はそれに合わせて変わらない（開いたループ）ので、正当な走りも転ぶ。また `Sim` は今、刻みを変えられない（`STEP_S` が物理エンジンの刻み・補助の式・経過時間に入っている） |
| 刻みを細かくして、方策で走らせ直し、崩れたら除く | 入力が状態に合わせて変わるので、正当な走りは崩れにくい | 刻みが違えば別の物理なので、タイムが変わるのは当たり前で、どこからを不具合とするかが決まらない |

- しきい値は、普通の走り（お手本の歩き方）と最初の実験の記録で出た値の、およそ 10 倍にした。関節が範囲を越えた量 0.05 rad・地面へのめり込み 0.02 m（どちらも 0.05 秒より長く続いたとき）、胴の跳ね上がり 0.25 m、胴の前後の速さ 5 m/s。出た値は ml/README.md にある
- 刻みの影響は、除く判定には使わず、参考の数字にする（まだ作っていない）。1/480 秒の刻みで、閉じたループで走らせ直し（②③ は重みで、① は歩き方の機械の値で）、1/240 秒とのタイムの差を記録する。刻みは `Sim` の引数で変える（[刻みを変えられるようにする](#刻みを変えられるようにする)）

### 再生の一致を守る

記録した入力を再生して、記録と同じタイムになるかを、`npm run check` のテストに入れる。`sim.ts` を変えると黙って崩れるので、物理を変えた人が、AI の記録も取り直す必要に気づけるようにする。

物理を変えてこのテストが落ちたとき。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **学習の流れを流し直して記録を作り直し、同じ PR で差し替える** | 理論値がいつも今の物理に合う。コマンド1つで済むようにする | 学習の分だけ時間がかかる |
| テストを理由つきで飛ばす（skip） | 物理の変更をすぐ入れられる | 理論値が古い物理のまま残る。飛ばしたことを忘れやすい |
| テストの期待するタイムだけ書き換える | 楽 | 古い物理で学んだ入力を新しい物理で再生したタイムで、理論値ではない。(E2) も確かめていない |

- 既定は作り直し。すぐにできないときだけ、テストを飛ばし、その理由をテストと PR に書く
- テスト（`src/screen/game/ai/theory.test.ts`）は、[モードの一覧](#モードの一覧)を回り、モードごとに記録をそのモードの物理で再生する。テストの名前は「<モード>：」で始める
- 記録の無いモード（一覧に足したばかり）も、テストを飛ばさずに落とす。落ちたときのメッセージで、CI が記録を作り、ブランチ `chore/retrain-<PR の番号>` から PR を出すので、それをマージするよう案内する。記録が入るまで、一覧にモードを足した PR を main に入れないため（入れると、main が「一覧にあるのに記録が無い」状態になり、そのあとの物理に関わる PR のたびに、そのモードの学習と記録の PR が出る）
- 一覧に無いモードの記録が残っていたら、落とす
- 上の「理由を書いて飛ばす」は、物理の変更を急いで入れたいときに、人が決めて行うもの。テストが自分で飛ばすことはしない

## 実験の管理

MLflow を使う。学習1回分の記録が run、比べ合う run をまとめる箱が experiment。レジストリは「使うもの」に番号（version）を振って並べる棚で、別名（alias）で「いま使っているのはどれか」を指す。

### レジストリに載せるもの

**入力の記録を載せる。** モデルはモードごとに分け、ノーマルは `funyaoji-10m-record`、ほかのモードは `funyaoji-10m-record-<モード>`（例：`funyaoji-10m-record-hard`）にする。version の中身は、毎秒30回の4つの値の列と、タイム・(E1)(E2) の結果・方法・元の run。記録は、そのモードの物理で再生して評価する。

- モードを分ける前からある version と別名を、そのまま使えるように、ノーマルのモデルの名前は変えない
- 別名（下の表）は、モデルごと、つまりモードごとに付く。候補にするのは、run のタグ `mode` がそのモードの run だけ（タグの無い前からの run はノーマル）

| 別名 | 指すもの |
|---|---|
| `theory` | (E2) を通った最速。見出しの理論値で、(b) で見せる |
| `theory-any` | (E1) の最速 |

| 案 | 良い点 | 悪い点 |
|---|---|---|
| 重みを載せる（試作） | (c) でそのまま使える | ① の探索には重みが無く、載らない。(a)(b) で使う記録は別に管理することになる |
| **入力の記録を載せる** | ①②③ を同じ物差しで並べられる。理論値とレジストリの中身が一致する | (c) の重みは別のモデルとして載せる |

- (c) をやるときは、重みを別のモデル（`funyaoji-partner` など）として載せる

### 別名の入れ替え

**自動。** 評価を通り、同じ物理の指紋の中で、記録を再生したタイムが今より速ければ、別名を移す。`theory` が変わったら、書き出す前に人が1回再生して目で見る。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **自動** | 物差しが決まっているので、人の判断が要らない | 判定に漏れがあると、不具合を突いた走りが見出しになる。書き出す前に人が見て補う |
| 手動（MLflow の画面で別名を移す） | 見てから決められる | 手間がかかり、基準がぶれる |

- 物理の指紋が変わったら、新しい指紋で最初に評価を通った記録が、速さに関係なく別名を取る。前の指紋の記録とは比べない
- 入れ替えは一度に1つずつ行う。別名の今の version を読み、移す直前にまだ同じ version を指しているときだけ移す（読んでから移すまでに変わっていたら、読み直して比べ直す）。並べて流した学習のうち、遅い方があとから終わって、速い方を上書きしないようにする

### 物理の指紋

**決まった入力の列を `Sim` で再生し、終わりの状態（各部位の位置・傾き、進んだ距離、経過時間、結果）からハッシュを作る。それに、実際に入っている Rapier の版を並べて記録する。** 入力の列は、接地や関節の範囲の端を通るもの（今のデモの歩き方など）にする。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **動きから作る（決まった入力を再生した結果＋Rapier の版）** | 物理を変えるものを、どこにあっても拾える。コメントを直しただけでは変わらない | 再生の分だけ時間がかかる（1回の走りなので短い） |
| `sim.ts` と `body.ts` の中身から作る（前の案） | 簡単 | ほかの所の変化を見落とす。Rapier の版（`package.json` は `^` で、実際の版は `package-lock.json` で決まる）、`src/shared/messages.ts` の `JOINTS` の順番（関節を作る順。順番で物理の結果が変わりうる）など。コメントを直しただけでも変わる |

- Rapier の版は、動きのハッシュが同じでも、どの版で出した記録かを読めるように足す
- 指紋はモードごとに作る（[モードの一覧](#モードの一覧)）。決まった入力の列を、そのモードの設定の `Sim` で再生する。入力の列はどのモードでも同じ。モードの名前はハッシュに入れない
- ノーマルの設定は空なので、ノーマルの指紋は、モードを分ける前と同じになる
- 確かめるのは `node scripts/rl/fingerprint.ts`。省くと一覧の全部のモードを、`--mode <モード>` でそのモードだけを確かめる
- 一覧に載っていないモードは、指紋を作らない。ハードは一覧に載っているので、ハードの物理（`HARD_MOTOR`・胴の補助を外すこと）を変えると、ハードの指紋だけが変わる。ノーマルの物理を変えると、ノーマルとハードの両方の指紋が変わりうる

### 記録するもの

| 種類 | 中身 |
|---|---|
| パラメータ | モード、方法（①②③）、報酬（R1/R2・G・k）、γ、学習の設定、環境の設定（人らしさの付け外しを含む）、乱数の種 |
| タグ | モード（`mode`）。コミットと、コミットしていない変更があったか。物理の指紋（[物理の指紋](#物理の指紋)） |
| メトリクス | 学習の経過（ゴール率・タイム）、評価（再生のタイム・ずらしたときのゴール率と中央値・(E1)(E2) の結果・刻みを細かくしたときのタイムの差） |
| 成果物 | 入力の記録、重み（②③）、経過 |

- 物理が変わると、前の記録は同じタイムを出さない。物理の指紋が違う記録どうしは比べない

### 比べ方

**比べる設定ごとに、乱数の種を3つ以上流し、中央値どうしで比べる。** 強化学習は乱数の種だけで結果が大きくぶれるので、1回ずつでは、たまたまの差を設定の差と見誤る。

最初の実験は、報酬2つ × γ 2つ × 種3つ ＝ 12 run。② は (R2) で歩き出さなかったので、比べ合いは ③ で流し、② は (R1) と (R2) を1本ずつ流した。

**学習は、決まった本数まで同時に流す（既定は 8 本）。** 1本の学習は、Node のプロセスを並べても、毎ステップ全部の返事を待つので CPU を使い切れない。8 本同時で、全体の速さは 1 本だけのときの約 1.7 倍になった。本数をそれより増やしても全体は速くならず、CPU も 3〜4 割しか使わない。この頭打ちの原因はまだ分かっていない（MLflow の SQLite ではないことは確かめた）。

### 学習の様子を見る

**学習の途中は、入力の記録だけを残す。動画は、学習の最後にまとめて作る。** 50 万ステップごとに、そのときの AI を、行動の乱数を使わずに1回走らせ、入力の記録を run に残す（2000 万ステップなら 40 個）。学習の最後に、いくつかの時点の記録を並べて同時にスタートさせた動画を作り、GIF と mp4 を run の成果物に残す。

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **途中の記録から、Node と Python で動画を作る** | Node で記録を再生して、コマごとの体の位置を出す。Python（Pillow）で絵にして、GIF と mp4 にする | 学習中に絵を描かないので、学習がほとんど遅くならない。自動で作れ、MLflow の画面で見られる | ゲームの描画（PixiJS）とは見た目が違う |
| 本番の画面で記録を再生して録画する | ゲームの描画のまま録る | 本番の見た目のまま | 人の手が要る。発表で見せたいものだけに使う |
| 学習中のおじさんを生で見る | 学習の環境から状態を画面に流し続ける | 見ていて楽しい | 並べた何十体のうちどれを映すか、学習を遅くしないか、の工夫が要る。作る量のわりに得が少ない |

- 物理は乱数を使わないので、入力の記録があれば、あとから何度でも同じ走りを再生できる。だから学習中に録画する必要が無い
- 並べた動画では、最初はすぐ転び、だんだん歩けるようになり、最後は速く走る様子が一目で分かる。(b) で見せる材料にもなる
- mp4 は `imageio-ffmpeg`（ffmpeg を同梱した Python のパッケージ）で作る。マシンに ffmpeg を入れなくてよい。MLflow の画面で GIF は見られる。mp4 は画面で再生できるか確かめていないので、両方残す

### 置き場所

**手元で動かす（SQLite の `ml/mlflow.db` と、フォルダの `ml/mlartifacts/`）。** リポジトリには入れない。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **手元で動かす** | 無料で、登録が要らない。サーバーを立てっぱなしにしなくてよい | 記録が1台の中にあり、ほかの人からは見えない |
| MLflow のサーバーを常に動かす | ほかのマシンからも記録・閲覧できる | 立てておく手間と、外から届く経路が要る。`MLFLOW_TRACKING_URI` を変えるだけで移れるので、必要になってからでよい |
| ホスト版（Databricks など）、Weights & Biases | 立てなくてよく、共有しやすい | アカウントの登録が要る。記録が外のサービスに出る |

- MLflow の CLI は、実験・run・成果物は操作できるが、レジストリへの登録と別名は操作できない（Python の API・REST・画面で操作する）。登録・別名・書き出しは、小さい Python のコマンドにまとめる
- 画面は `mlflow ui --backend-store-uri sqlite:///mlflow.db`（`ml/` で）で開く

### 物理の変更から記録の差し替えまでを自動にする

**次の流れを、GitHub Actions（`.github/workflows/ml-retrain.yml`）で自動にする。** スマホ向けの難しさの調整で、物理が変わる見込みがあるため。

1. 物理に関わるファイルを変えた PR で、PR をマージした結果の物理について、[モードの一覧](#モードの一覧)のモードごとに、物理の指紋を記録（`theory/<モード>.json`）のものと比べ、記録も再生する。記録が無いか、指紋が違うか、記録が同じタイムでゴールしなければ、そのモードは「変わった」とする
2. 変わったモードがあれば、CI がそのモードだけを、モードごとに学習の流れ（`ml/funyaoji_rl/pipeline.py --mode <モード>`）を流す。① の探索と、③・(R2)・γ 0.99 の学習を1本だけ流す。この設定は、ノーマルの最初の実験で種3つの中央値がいちばん速かったもの（いちばん速い1本の 6.804 秒は (R1) の run から出たが、差は種のぶれと同じくらい）。ほかのモードも同じ設定で流す
3. 流し終えたら、新しい記録を再生して、同じタイムになることを確かめる。そのあと、書き出した記録だけの動画を作る
4. 全部のモードの学習が終わったら、その時点の PR のマージした結果で、記録を確かめ直す（学習の数時間のあいだに、PR が進んでいることがあるため）。この実行の記録と、前に出した PR の記録のうち、今の物理で使えるものだけを選ぶ
5. 選んだ記録を1つのコミットにまとめて入れた PR を、CI が元の PR のブランチに向けて開く。もう開いていれば、本文を更新する
6. 人が動画を見て、マージする

- 「変わった」の判定と、再生の一致のテスト（[再生の一致を守る](#再生の一致を守る)）は、条件が違う。テストは「記録があり、再生して記録したタイムでゴールするか」だけを見る。判定はそれに加えて、物理の指紋が記録のものと同じかも見る
  - 記録が無いときと、再生のタイムが変わったときは、学習も始まり、テストも同じ PR で落ちる
  - 指紋だけが変わり、記録が今の物理でも同じタイムで再生できるとき（記録の走りが通らない所だけ物理が変わったときなど）は、学習は始まるが、テストは通る。だから記録の PR を待たずに元の PR をマージできてしまう。そうすると、記録の指紋が今の物理と違ったまま main に入り、そのあとの物理に関わる PR のたびに、そのモードが「変わった」となって学習し直しになる。記録の PR（記録の指紋を今の物理のものにそろえ、タイムは学習し直したものになる）をマージしてから、元の PR をマージする
- 一覧にモードを足したときも、そのモードの記録が無いので「変わった」となり、記録を作る PR が出る。モードを足す人は、強化学習の側を触らなくてよい。記録の PR をマージするまで、モードを足した PR のテストは落ちる
- 2つ以上のモードが同時に変わったときは、モードごとに別のマシンで並べて流す（matrix）。順に流すと、1回で最大 5 時間半の学習がモードの数だけ積み重なり、PR が出るまでが長くなる。GitHub のマシンは並べても同時に動かせる数に余裕がある（self-hosted のランナーが1つなら、順に流れる。[どこで学習を流すか](#どこで学習を流すか)）
- どれかのモードの学習が落ちても、ほかのモードの学習は止めない。PR は、全部のモードが通ったときだけ出す。落ちたモードだけを「Re-run failed jobs」で流し直せば、通ったモードの記録（同じ実行の成果物）と合わせて PR が出る
- 手で流すときの `force` は、一覧の全部のモードを学習し直す。記録が使えるモードも、学習した記録を今の物理で確かめ直して、使えれば PR に出す

- これは、Google Cloud の MLOps の成熟度の段階でいう「レベル1」（学習の流れを自動で回し、データや条件が変わるたびに学習し直す。継続的な学習）にあたる
- CI のマシンは CPU のコアが少ないので、1回の学習し直しは流せるが、設定の比べ合い（12 run など）は流せない。比べ合いは手元で続ける。学習のジョブだけは、チームのマシンでも流せる（[どこで学習を流すか](#どこで学習を流すか)）
- ワークフローが作った・更新した PR では、GitHub の決まりで CI が自動で流れないか、承認待ち（「Approve and run」）になることがある。記録の PR の Checks の欄と、Actions の画面で、CI が流れたかを確かめる。承認待ちなら承認し、流れていなければ閉じて開き直す
- 学習と確かめ直しは、書き込みの権限を持たないジョブで流す。ブランチの push と PR を開くところだけを、PR のコードを動かさない別のジョブ（publish）に分ける
- おかしいときは、黙って成功せずにジョブを落とし、再実行で回復できるようにする。落ちた実行には、ほかの実行も任せない（[同じ物理の学習](#物理の変更から記録の差し替えまでを自動にする)の判定）ので、次の実行が学習し直す
- verify は、PR のマージした結果の計算が終わるまで待ち、マージした結果の親が、読んだ PR の head と base かを確かめる。待っても終わらないときと、API のエラーでは落ちる。PR がぶつかっているときと、閉じられたときは、PR を出さずに終わる
- 記録の確かめ（`fingerprint.ts`）は、終了コードで「使えない（1）」と「確かめられなかった（2）」を分ける。ワークフローは、確かめられなかったときと、出力の形が違うときは落ちる
- publish は、書く前と push の直前に、PR が開いていて、verify が確かめたときと同じ head と base を指しているかを確かめる（手で流したときは、ブランチの先頭が同じか）。動いていたら落ちる。そのときは、新しい実行に任せるか、この実行の「確かめ直す」のジョブを選んで再実行する（PR を出すジョブも流れ直す）。base（main など）が物理と関係ない変更で進んだときも落ちるので、そのときも同じように再実行する
- publish は verify の出力をそのまま信じず、モードの名前（`^[a-z][a-z0-9-]*$`・重複なし）、SHA（40桁の16進数）、記録のファイル（通常のファイル・JSON・要るフィールド・指紋）を確かめる。ステージするのは `src/screen/game/ai/theory/<モード>.json` だけ
- 前に出した PR のブランチは、確かめ直したときから変わっていないときだけ上書きする（`--force-with-lease`）。古い実行が、新しい物理向けの記録を上書きしないようにするため
- ワークフローの定義そのものは、PR のブランチのものが動く。同じリポジトリの PR はワークフローの定義を変えられる、という前提は、main の CI と同じ（信じられる ref に定義を置くことはしていない）
  - 物理がまた変わり、使える記録が無いモードは書かない。使えるモードの記録だけで PR を出し、残りは新しい実行が作る
  - 前に出した PR の記録も候補にするので、別の実行が先に出したモードの記録を消さない
- 同じ物理で学習が流れていれば、新しく流さない。物理がまた変わったときだけ、流れている学習を止めてやり直す。PR を少し直すたびに、数時間の学習がやり直しにならないようにする
  - 実行の照らし合わせと、ジョブを止める単位（concurrency）のキーは、PR の番号（`pr-<番号>`）。手で流したときは `dispatch-<ブランチ>`。同じ head のブランチから別の base に出した PR や、手で流した実行が、互いの学習を止めないようにする。キーは実行の名前（run-name）の末尾の `[キー]` に入れ、それで同じキーの実行を探す
  - 学習・確かめ直し・PR を出すジョブの名前に「（モード・指紋）」を入れる。同じキーの終わっていない別の実行が、学習し直すモードの全部を同じ指紋で受け持っていれば任せ、1つでも違えば、変わった全部のモードを流し直す。前の実行は全部のモードがそろわないと PR を出さないので、一部のモードだけを前の実行に任せると、そのモードの記録が PR に入らないため
  - 受け持っているとみなすのは、そのモードのジョブが進んでいるか、学習が成功して終わり、その記録が成果物に残っているとき。失敗・取り消しで終わったジョブがある実行は、PR まで進まないので任せない
  - 学習のジョブが、ランナーを待ってキューにいる（まだ始まっていない）実行には任せない。self-hosted のランナーが止まっているときに、変数を消して流し直せば、新しい実行が学習を始め、古い実行の学習は concurrency が止める（[どこで学習を流すか](#どこで学習を流すか)）
  - 学習を止める単位は、キー（PR）とモードの組。同じ実行の別のモードの学習どうしは止め合わない
  - 前に出した PR（ブランチ `chore/retrain-<PR の番号>`）が開いていて、その記録が学習し直すモードの全部で今の物理で使えるなら、学習し直さない。ブランチだけが残っている（PR を閉じた）ときは、学習し直して出し直す
- ワークフローに PR を開かせるには、リポジトリの設定「Allow GitHub Actions to create and approve pull requests」が要る。開けなかったときは、手で PR を開くためのリンクを出して止まる
- ブランチの push は済んで、PR を作る・直すところだけが落ちたときは、PR を出すジョブだけを再実行しても、前に出した PR のブランチが確かめたときから変わっているので回復しない。エラーに出たリンク（`compare/<元の PR のブランチ>...chore/retrain-<PR の番号>?expand=1`）から、手で PR を開く
- 物理の指紋は、お手本の歩き方に加えて、関節を入力の両端まで動かす入力の列も再生して作る。お手本は入力を 0.76 までしか使わないので、入力の上限などを変えても、お手本だけでは指紋が変わらない

CI で流した run の記録。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **ワークフローの成果物（Artifacts）として残す（`mlflow.db`・成果物・動画、30 日）** | サーバーが要らない。ダウンロードして `mlflow ui` で開ける | 手元の MLflow とは別になる。30 日で消える |
| MLflow のサーバーを立て、CI からそこに記録する | 記録が1か所にまとまる | サーバーを立てておく手間と、CI から届く経路と秘密が要る |

CI で学習し直して、前より遅くなったとき。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **前より遅くても差し替える** | 物理が変わったので、前の記録とは比べない（[別名の入れ替え](#別名の入れ替え)と同じ考え方）。テストがすぐ通る | 学習の運で、理論値が本当の最速より遅く出ることがある。気になれば、手元で何本か流して差し替える |
| 前より遅ければ差し替えない | 理論値が下がらない | 古い物理の記録は、新しい物理で同じタイムを出さない。テストが落ちたままになる |

### どこで学習を流すか

**学習のジョブ（`retrain`）だけを、リポジトリの変数で、チームのマシンの self-hosted runner に切り替えられるようにする。変数が無ければ GitHub のマシンで流す。** GitHub のマシンは CPU が少なく、1回の学習に数時間かかる。コアの多いマシン（24 コア）なら約 35 分で終わる。指紋を比べる・確かめ直す・PR を出すジョブ（`fingerprint`・`verify`・`publish`）は、いつも GitHub のマシンで流す。ランナーの立て方は [ml/runner/README.md](../ml/runner/README.md) にある。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **学習のジョブだけを self-hosted で流す（変数で切り替える）** | 速い。書き込みの権限を持つジョブ（`publish`）は GitHub のマシンのまま。変数を消せばすぐ戻せる | マシンを立てておく手間。公開リポジトリなので、PR のコードがチームのマシンで動く（下の注意） |
| 全部を GitHub のマシンで流す（今まで） | 立てる手間が無い | 1回に数時間かかる |
| GitHub の大きいマシン（larger runner） | 立てる手間が無い | お金がかかる |

| リポジトリの変数 | 値 | 無いとき |
|---|---|---|
| `ML_TRAIN_RUNNER` | 学習のジョブの `runs-on` のラベルを、JSON の配列で書く。`["self-hosted","linux","x64","funyaoji-ml"]` | `ubuntu-latest`（GitHub のマシン） |
| `ML_TRAIN_WORKERS` | 学習で並べる Node のプロセスの数。128 の約数（1・2・4・8・16・32・64・128）。24 コアなら 16 | 4（`ML_TRAIN_RUNNER` が無いときも 4） |

- 変数は、GitHub のマシンで動く `fingerprint` のジョブが確かめてから、学習のジョブに渡す。`ML_TRAIN_RUNNER` は、`funyaoji-ml` を含む、ラベルの形の文字列の配列だけを許す（小文字にそろえ、重なりを除く）。`ML_TRAIN_WORKERS` は、上の8つの文字列のどれかだけを許す。違えば、変数の名前を入れたエラーで `fingerprint` が落ちる
- `ML_TRAIN_RUNNER` があるときは、`fingerprint` が「学習は self-hosted（funyaoji-ml）で流れる」を実行の Summary に出す

- 並べる数を変えても、体の数の合計（128 体）は変えない（1プロセスあたり 128 / `ML_TRAIN_WORKERS` 体）。物理は乱数を使わず、体ごとに別の物理で動き、プロセスをまたいでも体の並び順は同じなので、合計が同じなら、同じマシンでは学習の結果は変わらない（ランナーのコンテナで、30 万ステップを 4×32 体と 16×8 体で流し、学習の経過と評価の数字がすべて同じだった。① の記録も、4 と 16 のプロセスで同じだった）。① の探索（`openloop.py`）も、歩き方ごとに物理を作り直して走らせるので、プロセスの数で結果は変わらない。PyTorch のスレッドの数（`--torch-threads 2`）は変えない
  - マシン（CPU）が違うと、PyTorch の計算の端数が変わり、同じ種でも学習の結果が変わることがある。記録は、どのマシンで作っても、再生して同じタイムになることを確かめてから出す（`theory.test.ts`・`fingerprint.ts`）ので、困らない
- `timeout-minutes`（330 分）は、self-hosted でも同じにする。self-hosted には GitHub のマシンの6時間の上限が無いので、止まったジョブがマシンを使い続けないための上限として残す
- ランナーが1つなので、学習し直すモードが2つ以上あるときは、1つずつ順に流れる（それでも GitHub のマシンで並べるより速い）
- ランナーが止まっていると、学習のジョブはランナーを待ち（ジョブの状態が「Queued」で、「Waiting for a runner to pick up this job」と出る）、24 時間で落ちる。マシンを長く止めるときは、変数 `ML_TRAIN_RUNNER` を消す。消したあとに新しく流した実行（PR に push する・手で流す）から、GitHub のマシンに戻る

#### ランナーが止まっていて、学習が始まらないとき

- 気づき方：実行の Summary に「学習は self-hosted（funyaoji-ml）で流れる」と出ているのに、学習のジョブが「Queued」のまま進まない。Settings → Actions → Runners に `funyaoji-ml-...` が「Idle」で無い
- 直すか、GitHub のマシンに切り替える
  1. マシンの持ち主に、ランナーを立ち上げ直してもらう（[ml/runner/README.md](../ml/runner/README.md) の「困ったとき」）。立ち上がれば、待っていたジョブがそのまま流れる
  2. すぐに戻らないときは、管理者が変数 `ML_TRAIN_RUNNER` を消す。キューで待っている実行を Cancel してから、流し直す（PR に push するか、Actions の画面から手で流す）
- 学習がランナーを待ってキューにいる（まだ始まっていない）実行は、「同じ物理の学習が進んでいる」とみなさない（[物理の変更から記録の差し替えまでを自動にする](#物理の変更から記録の差し替えまでを自動にする)）。なので、Cancel し忘れても、新しい実行は学習を始め、古い実行の学習は concurrency が止める。ただし、ランナーが拾うまでの数秒のあいだに新しい実行が来ると、同じ物理の学習がもう一度始まる（古い方が止まるだけで、困らない）

#### ランナーのしくみ

ランナーは、チームのマシン（Windows・Docker Desktop・24 コア）の上の、Docker の Linux コンテナで動かす。設定は [ml/runner/](../ml/runner/) にある。

| コンテナ | 持つもの | 動かすもの |
|---|---|---|
| manager（1つ。ずっと動く） | 登録の秘密（PAT）、Docker のソケット | GitHub から、1回きりの JIT の設定（`generate-jitconfig`）を取り、その設定だけを渡してジョブのコンテナを起こし、終わるのを待つ。これを繰り返す。ジョブのコードは動かさない |
| ジョブのコンテナ（1つのジョブごとに作って捨てる。`docker run --rm`） | 1回きりの JIT の設定だけ | ランナーの本体を、最初から `runner` のユーザーで動かし、ジョブを1つ流して終わる |

- PAT は manager にだけ渡す。ジョブのコンテナには、PAT も Docker のソケットもホストのフォルダも渡さない
- ジョブのコンテナの中では、root が何も動かさない。`sudo` は消してある。ランナーの本体は root の持ち物で、ジョブからは書き換えられない。だれでも書けるファイルが無いことを、イメージを作るときに確かめる
- ジョブのコンテナは、権限（capabilities）を全部外し（`--cap-drop ALL`）、権限を上げさせず（`no-new-privileges`）、CPU・メモリ・プロセスの数に上限を付ける
- ジョブのコンテナは毎回新しく作るので、前のジョブが何を書いても、次のジョブには残らない
- JIT のランナーは、ジョブを1つ流すと GitHub が登録を消す。ジョブを受け取らないまま manager を止めたときは、manager が登録を消す

#### 公開リポジトリで self-hosted を使う注意

GitHub は、公開リポジトリで self-hosted runner を使うことを勧めていない。PR のコードが、チームのマシンで動くからだ。次の決まりで、動くコードと届く範囲を絞る。

**残る危うさ（そのまま受け入れるもの）。**

- **書き込みの権限を持つ人は、このマシンの上でコードを動かせる。** 同じリポジトリの PR はワークフローの定義を変えられるので、どのジョブでもランナーに載せられる。チームの人を信用する前提で使う。書き込みの権限は、チームの人だけに渡す
- **ジョブのコンテナから、ホストの localhost のサービス（`host.docker.internal`）と、マシンと同じ LAN に届く。** Docker Desktop のコンテナは、ホストと LAN に出られる

**動くコードと届く範囲を絞る決まり。**

- **流れるのは学習のジョブだけ。** ほかのジョブとほかのワークフローは `ubuntu-latest` のまま。ランナーには固有のラベル `funyaoji-ml` を付け、ほかのジョブが間違って載らないようにする
- **フォークからの PR では流れない。** `fingerprint` と `retrain` の `if` が、`workflow_dispatch` か、同じリポジトリのブランチからの PR だけを通す
  - ただし、フォークからの PR では、ワークフローの定義もフォークのものが動くので、`if` を消した定義を送られると止められない。**本当の守りは、下のリポジトリの設定（承認）**。管理者は、フォークの PR の「Approve and run」を押す前に、`.github/workflows/` の変更を読む
- **ランナーは使い捨てにする。** ジョブを1つ流すたびに、ジョブのコンテナを作って捨てる（上の「ランナーのしくみ」）。学習のジョブも、始めに作業フォルダが空であることを確かめる
- **ホストに触れるものと秘密を、ジョブに渡さない。** ジョブのコンテナに、Docker のソケット・ホストのフォルダ・PAT を渡さない。ジョブの `GITHUB_TOKEN` は読むだけ（`contents: read`）で、ほかの秘密も渡さない

**残る危うさを小さくする設定（マシンの持ち主）。**

- Docker Desktop の Settings → General の「Expose daemon on tcp://localhost:2375 without TLS」を切る。入っていると、ジョブのコンテナから `host.docker.internal:2375` で Docker を操作でき、ホストを乗っ取れる
- ホストで `0.0.0.0`（全部の口）に開いている開発用のサービス（データベース・開発サーバー・管理画面など）に気をつける。ジョブのコンテナから届く。ランナーを立てているあいだは止めるか、`127.0.0.1` だけに開く。ただし Docker Desktop では、`127.0.0.1` に開いたサービスにも `host.docker.internal` から届くことがあるので、守るべきものはランナーのマシンに置かない
- LAN に守るべきもの（ほかの人の PC・家の機器の管理画面など）があるマシンでは立てない

#### 管理者（リポジトリの持ち主）がやること

ランナーの登録とリポジトリの設定には、リポジトリの管理者の権限が要る。

1. **フォークの PR の承認**：Settings → Actions → General の「Approval for running fork pull request workflows from contributors」を「Require approval for all outside collaborators」にする
2. **登録の秘密**：fine-grained PAT を作る（Settings → Developer settings → Personal access tokens → Fine-grained tokens）。Repository access は「Only select repositories」でこのリポジトリだけ、Repository permissions は「Administration」を「Read and write」だけ。期限を付ける（90 日など）。マシンの持ち主に、チャットや Issue に貼らずに渡す（パスワードの管理ツールの共有など）。PAT は manager のコンテナだけが持ち、1回きりの JIT の設定を取るのに使う
3. **変数**：Settings → Secrets and variables → Actions → Variables に、`ML_TRAIN_RUNNER`（`["self-hosted","linux","x64","funyaoji-ml"]`）と `ML_TRAIN_WORKERS`（`16`）を作る。ランナーが Settings → Actions → Runners に「Idle」で出てから作る
4. **確かめる**：Actions の「理論値の記録の作り直し」を、`force` を付けて手で流し、学習のジョブがランナー（`funyaoji-ml-...`）で流れ、記録の PR が出ることを見る

- やめるとき・戻すとき：変数 `ML_TRAIN_RUNNER` を消す。急ぐときは、Settings → Actions → Runners からランナーも消し、PAT を取り消す
- PAT の期限が切れると、ランナーは登録できなくなる。期限の前に作り直して渡す

## 配布と見せ方

### 入力の記録の置き場所

**`src/screen/game/ai/theory/<モード>.json` に JSON で置き、リポジトリに入れる（ノーマルは `theory/normal.json`）。** 置くのは、モードごとの `theory` の記録だけ。モードの名前は[モードの一覧](#モードの一覧)のキーと同じ。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **`theory/<モード>.json`（モードごとにファイルを分け、フォルダにまとめる）** | モードを足しても、ほかのモードのファイルに差分が出ない。CI がモードごとに作った記録を、ファイルを置くだけで差し替えられる。テストはフォルダを読めば、全部のモードの記録が分かる | 前の `theory.json` から場所が変わる（読んでいたのはテスト・`fingerprint.ts`・`registry.py`・ワークフローだけ） |
| `theory.json` の中にモードごとに入れる | ファイルが1つ | モードを1つ差し替えるたびに、ほかのモードも入ったファイルを書き換える。並べて流した学習の記録をまとめるのに、JSON を組み直す手間が要る |
| ノーマルは `theory.json` のまま、ほかを `theory-<モード>.json` | ノーマルの場所が変わらない | モードで決まりが違い、読む側に分かれ道が要る |

ファイルの置き方とは別に、そもそもどこに置くか。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **リポジトリに入れる** | プレビューでも本番でも、そのまま動く。どの記録で動いているかが PR で分かる | 差し替えるたびに差分が出る |
| ページを開いたときに MLflow から取る | 差し替えにコミットが要らない | MLflow を外から見える場所に置く必要がある |
| R2 などの置き場所に上げる | リポジトリが太らない | 上げる手順と権限が増える。数 KB なので、太る心配が無い |

どの記録を置くか。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **`theory` だけ** | ゲームが見せるのはこれだけ。不具合を突いたかもしれない走りを配らない | (E1) の走りは、手元の MLflow でしか再生できない |
| `theory` と `theory-any` | (E1) の走りも誰でも再生できる | ゲームで使わないものが入る |

- `theory-any` は MLflow に置いたままにし、そのタイムはドキュメント（このファイル）に書く
- 大きさは、1回分（約 7.5 秒 ＝ 225 ステップ × 4つの値）で約 5 KB。学習の上限時間（30 秒）まで走っても約 22 KB。差し替わるのは理論値が更新されたときだけ
- 環境は、AI の行動を物理に渡す前に 1/1000 の目盛りにそろえる。記録はその値を小数3桁でそのまま書く。書き出すときに丸めると、記録と再生でタイムが変わる（試作では、重みを丸めただけで 8.67 秒が 13.54 秒になった）。①②③ のどの方法も、同じ目盛りを通す
- 目盛りにそろえるのは、Node の側で、倍精度（JavaScript のふつうの数）で `Math.round(u * 1000) / 1000` とする。Python の float32 でそろえると、0.123 が float32 では 0.123 ぴったりにならず、記録に書いた「0.123」を読み直した値と、学習のときに物理に渡した値がずれる
- 1/1000 は傾きで 0.09 度で、スマホのセンサーのぶれより細かい。スマホが送る傾き（`angle`）の細かさは、[通信の仕様](api.md) にまだ決まっていない。整数に丸めない作り（まだ main に入っていない PR #99）のとおりなら、ゲームの入力より粗くしたことにはならない。細かさが決まったら見直す

### ゲームのどこで見せるか

検討中。企画とゲームの進行の話なので、決めたら [企画書](product.md) と [ゲームの進行](game.md) に仕様を書いてから作る。

| 案 | 中身 |
|---|---|
| ロビーで流すお手本 | 人を待つ間、AI の走りを流す |
| AI の記録との対決 | プレイ中、半透明の AI のおじさんが同じコースを走る（ゴースト） |
| ランキングに AI の記録を載せる | 「理論値」として、目標の1行にする |

- どの案も、記録を画面の時間に合わせて再生するだけで作れる（[再生をそろえる](#再生をそろえる)）

### (c) の重み

やるときに決める。重みを JSON にして、ブラウザの TypeScript で計算する形（試作の `policy.ts`）が候補。推論のサーバーも追加のライブラリも要らず、会場の回線に左右されない。

## 結果

2026-11-28 の最初の実験の結果。細かい数字は ml/README.md にある。

| 方法 | タイム |
|---|---|
| ① 決まった歩き方（CMA-ES） | 7.337 秒 |
| ② PPO だけ・(R1) | 8.479 秒（(R2) では歩き出さなかった） |
| ③ ① を土台に PPO が補正 | 6.804〜6.946 秒（12 run・24 記録） |

- **理論値は 6.804 秒**（毎秒30回・4つの関節を同時に切り替える条件）。(E1) と (E2) は同じ記録で、物理の不具合を突いた走りは無かった
- ③ は ① より約 0.5 秒（7%）速い。体の状態を見て補正することに意味がある
- ② の (R2) は、[報酬](#報酬) で書いた弱点（一度もゴールしないうちは手がかりが弱い）のとおり、2000 万ステップでも歩き出さなかった
- ③ では γ 0.99 が 0.995 より速く、報酬は (R2) が少し速かった（差は種のぶれと同じくらい）

### ハードモード

2026-11-28 に、CI と同じ流れ（`pipeline.py --mode hard --steps 20000000`。① の探索と、③・(R2)・γ 0.99・種 0 を1本）を手元で1回流した。物理の指紋は `19179f6b4eef`（Rapier 0.21.0）。設定は CI と同じで、並べる Node のプロセスだけを増やした（16 プロセス × 8 体。体の数の合計 128 は CI の 4 × 32 と同じ）。① と ③ を合わせて約 35 分（① が約 40 秒、③ の 2000 万ステップが約 33 分）。

| 方法 | タイム |
|---|---|
| ① 決まった歩き方（CMA-ES） | 8.421 秒（T 1.81・h0 0.70・A 0.67・K 0.72・kp 0.01） |
| ③ ① を土台に PPO が補正 | 7.446〜7.450 秒（そのままの1回 7.450 秒、ずらした 16 回の中央値 7.458 秒・ゴール率 100%） |

- **ハードの理論値は 7.446 秒**（毎秒30回・4つの関節を同時に切り替える条件）。(E1) と (E2) は同じ記録で、ゴールした 17 の走りはどれも (E2) を通った。記録は `src/screen/game/ai/theory/hard.json`
- ノーマル（6.804 秒）より約 0.64 秒遅い
- ① は、お手本の歩き方（ハードでは約 1.8 秒で後ろに転ぶ）から探し始めて、2 世代目でゴールする歩き方を見つけ、60 世代目までに 8.421 秒に縮めた。見つけた歩き方は、ももの中心 h0 を 0.70 と前に寄せて胴を前に傾けるもので、docs/game.md の「ハードモード」で分かっていたことと合う。どの値も ① の探す範囲（h0 −0.5〜0.8・A 〜1.6・K 〜1.6）の端には張り付いていないので、範囲はノーマルと同じままにした
- ③ は、行動の乱数を使わない走りでは学習の前（ほぼ土台のまま）から 10m に着き、50 万ステップごとの走りのタイムが 9.07 秒（学習の前。出力の平均が 0 でないので、① より遅い）から 7.44 秒まで縮んだ。行動の乱数を入れた学習中の走りは、最初はすべて転んだが、約 100 万ステップでほぼ全部（99.8%）がゴールするようになった
