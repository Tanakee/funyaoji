# 設計

システム構成と技術の選定理由を書く。ゲームの内容（コンセプト・ルール・スコープ）は[企画書](product.md)、通信の仕様は [API](api.md)、状態の遷移と画面は[ゲームの進行](game.md)にある。

## システム構成

```
スマホ（4台）  ──傾き──→  サーバー  ──4人の傾き──→  スクリーン
              ←─状態──            ←────状態────
```

| コンポーネント | 役割 | 実行環境 |
|---|---|---|
| スマホ | 傾きを読み取って送信する。担当の関節と入力の状態を表示する | 参加者のスマホのブラウザ |
| サーバー | ルームを管理し、スマホとスクリーンの間でメッセージを中継する。ランキングを保存する | Cloudflare Workers と Durable Objects |
| スクリーン | 物理演算と描画を行う。QR コード・タイム・ランキングを表示する | 会場のスクリーンに接続した PC のブラウザ |

- 物理演算はスクリーンだけで行う。全員が同じ画面を見るので、シミュレーションは1か所で足りる。サーバーはメッセージを中継するだけで、ゲームの状態を計算しない

## 技術スタック

| 領域 | 採用 | 理由 | 見送った案 |
|---|---|---|---|
| リアルタイム通信 | WebSocket。あとから WebRTC DataChannel を追加する | WebSocket はどの回線でも接続できる。WebRTC は低遅延だが、回線によっては P2P で接続できない | WebRTC のみ（当日接続できないリスクがある） |
| バックエンド | Hono、Durable Objects | Hono は Cloudflare Workers で広く使われ、ルーティングを短く書ける。Durable Objects はルームごとに1つのインスタンスで WebSocket を保持できる | Node.js のサーバー（無料のホスティングはスリープする） |
| 物理エンジン | Rapier 2D | 関節のモーターに目標角度を直接指定できる。同じ入力から同じ結果になるビルドがある | Planck.js（目標角度の制御を自作する）、Matter.js（関節のモーターが無い） |
| 描画ライブラリ | PixiJS | スプライトとフィルタがある。物理エンジンを自由に選べる | Canvas 2D（演出をすべて自作する）、Phaser（付属の物理エンジンが前提になる） |
| ゲームエンジン | 不採用 | チームに経験が無い。コードだけで開発でき、差分をレビューしやすい | Godot、Unity |
| フロントエンド | React、Vite+ | チームに React の経験がある。Cloudflare の公式ガイドがある | フレームワークなし、Svelte 5 |
| 言語 | TypeScript | クライアントとサーバーで型定義を共有できる | |
| ホスティング | Cloudflare Workers | 静的アセットと API を同じ Worker にデプロイできる。HTTPS が標準で付き、無料枠で足りる | |
| 環境とデプロイ | ローカル・プレビュー・本番の3つ。プレビューは Workers Previews で PR ごとに自動で作り、本番は手動でデプロイする | PR ごとに別の URL と別の Durable Objects のストレージができ、並行して開発してもぶつからない。本番を手動にすると、発表の前に壊れた変更が出ない | GitHub Actions、プレビューを作らない、共有のステージングを1つ持つ（[環境とデプロイ](#環境とデプロイ)） |
| CLI | `cf` | `wrangler` の後継。公開ベータなので、未対応の操作は `wrangler` を使う | |

### リアルタイム通信

- 先に WebSocket だけでロビーから結果までを動かす。そのあとで WebRTC DataChannel を追加する
- WebRTC に移すのは到達保証が不要なメッセージだけ（[API](api.md)）。WebRTC で接続できないときは WebSocket にフォールバックする
- WebRTC を追加する時間が無ければ WebSocket だけにする

### フロントエンド

- React が担当するのは UI（ロビー・タイム・結果・ランキングと、スマホのボタン）だけ。フレームごとの描画と通信は React の外に置く
- Vite+ が Cloudflare の Vite プラグインと Durable Objects で動作しなければ Vite に切り替える

### 環境とデプロイ

| 環境 | 内容 | 更新の方法 |
|---|---|---|
| ローカル | 各自の PC。Hono も Durable Objects もローカルで動く。スマホの実機では Cloudflare Tunnel（Quick Tunnel）の HTTPS の URL で開く | 開発サーバーを動かす |
| プレビュー | Cloudflare の Workers Previews。PR ごとに URL と Durable Objects のストレージが作られ、URL は PR のコメントに表示される | PR に push すると、Cloudflare の GitHub App が自動で更新する |
| 本番 | 発表で使う環境。URL は `workers.dev` | 手動でデプロイする（`wrangler deploy` か、Cloudflare のダッシュボード） |

- 傾きの読み取りには HTTPS が要る。ローカルの開発サーバーを Tunnel で公開すると、デプロイせずにスマホの実機で確かめられる
- プレビューと本番は、Durable Objects のストレージが分かれる。ルームとランキングのデータは混ざらない
- 本番は main にマージしても更新しない。main を試すときは、各自のローカルで動かす
- 本番が壊れたときは `wrangler rollback` で前の版に戻す
- GitHub の連携は、Cloudflare の GitHub App を使う。App はリポジトリの所有者がインストールする。インストールされるまでは、プレビューも手元から `wrangler preview` で作る
- Workers Previews の操作（`wrangler preview`）は `cf` で行えないため、`wrangler` を使う
- 独自ドメインは、余裕があれば設定する

| 見送った案 | 理由 |
|---|---|
| GitHub Actions でデプロイする | Cloudflare の API トークンをリポジトリの Secrets に登録する必要があり、ワークフローと PR へのコメントを自作することになる。GitHub App で同じことができる |
| プレビューを作らない | レビューする人が自分で動かす必要があり、スマホ4台での確認がしにくい |
| 共有のステージングを1つ持つ | 2人が同時に試すと上書きし合う |
| 本番を main へのマージで自動で更新する | 発表の直前に、壊れた変更がそのまま本番に出るおそれがある |
| Version URLs（以前の Preview URLs） | Durable Objects を使う Worker では作られない |

### 物理エンジン

- 人形が安定しないなど、Rapier 2D で行き詰まったときは Planck.js を試す

## ディレクトリ構成

```
src/
  shared/   メッセージの型定義と、共通の定数
  server/   サーバー（Hono のルーティングと、ルームの Durable Objects）
  net/      通信のクライアント（WebSocket の接続と再接続。WebRTC はここに追加する）
  phone/    スマホのページ（傾きの読み取りと、UI）
  screen/
    game/   物理演算と描画。React と通信に依存しない
    ui/     スクリーンの UI（React）
docs/       ドキュメント
```

- パッケージは1つにする。設定が1つで済み、`shared/` を import するだけで型定義を共有できる
- `screen/game/` の入力は関節ごとの目標角度、出力は距離・ゴール・転倒のイベントにする。入力元がキーボードでもスマホでも同じインターフェースになり、物理演算と通信を並行して開発できる

| ディレクトリ | 担当 |
|---|---|
| `server/` | バックエンドの担当 |
| `net/`、`phone/` の傾きの読み取り | 通信の担当 |
| `screen/game/` | フロントエンドのリード |
| `screen/ui/`、`phone/` の UI | 未定 |
| `shared/` | 全員。変更は PR でレビューを受ける |

## 完成の定義

事前開発の終わり（11/27）に、企画書の「Must」の4つが 10m モードで、スマホ4台で通して動く。

## 決定の記録

| 日付 | 決定事項 | 理由 |
|---|---|---|
| 2026-11-18 | フレームワークを使わない縛りはやらない | 期間が短く、リアルタイム性にも響くおそれがある |
| 2026-11-19 | 物理演算はスクリーンだけで行う | 全員が同じ画面を見るので、1か所で足りる。サーバーは中継だけになり、実装が減る |
| 2026-11-19 | ゲームエンジン（Godot・Unity）は使わない | チームに経験が無く、覚える時間が取れない。コードだけで進められる形にする |
| 2026-11-19 | 通信は WebSocket（Cloudflare Workers と Durable Objects）で作り、WebRTC を足す | WebSocket は確実につながる。WebRTC は速いが、回線によってはつながらない。両方あれば、速さと確実さがそろう |
| 2026-11-19 | 描画ライブラリは PixiJS | スプライトとフィルタがある。物理エンジンを自由に選べる |
| 2026-11-19 | フロントエンドは React と Vite+。言語はすべて TypeScript | チームに React の経験があり、すぐに書き始められる。クライアントとサーバーで型定義を共有できる |
| 2026-11-19 | 物理エンジンは Rapier 2D | 関節のモーターに目標角度を直接指定できる。2つを作って比べる時間は、ほかに使う |
| 2026-11-19 | バックエンドは Hono と Durable Objects | Cloudflare Workers でよく使われ、ルーティングを短く書ける |
| 2026-11-19 | 転んだらやり直し。起き上がれない | 難しさがこのゲームの面白さで、何度もやり直す遊び方を想定する |
| 2026-11-19 | 誰かが切断したら、そのプレイは終了 | 1人が1か所を担当するので、欠けると走れない |
| 2026-11-19 | 遊び方を「モード」で選ぶ。MVP は 10m モードだけ | 4人で操作するのは難しく、50m は遠い。距離を変えるだけなので「難易度」とは呼ばない。競技らしさは出さないので「種目」とも呼ばない |
| 2026-11-19 | タイムアウトは120秒 | 放っておかれたプレイを終わらせるため。仮の値で、遊んで直す |
| 2026-11-19 | 開始とやり直しはスクリーンの PC で操作する。スマホからの「もう一度」は Should | MVP で作る量を減らす。スマホからやり直せると快適なので、次に足す |
| 2026-11-19 | 距離はマイナスも扱う | 後ろに進むことがあり、それも結果として見せる |
| 2026-11-20 | Cloudflare の CLI は `cf` を使う | `wrangler` の後継。公開ベータなので、未対応の操作は `wrangler` を使う |
| 2026-11-20 | 環境はローカル・プレビュー・本番の3つ。プレビューは PR ごとに自動で作り、本番は手動でデプロイする | PR ごとに試せて、並行して開発してもぶつからない。本番を手動にすると、発表の前に壊れた変更が出ない |
