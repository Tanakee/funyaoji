# 設計

システム構成と技術の選定理由を書く。ゲームの内容（コンセプト・ルール・スコープ）は[企画書](product.md)、通信の仕様は [API](api.md)、状態の遷移と画面は[ゲームの進行](game.md)にある。

## システム構成

```
スマホ（4台）  ──傾き──→  サーバー  ──4人の傾き──→  スクリーン
              ←─状態──            ←────状態────
```

| コンポーネント | 役割 | 実行環境 |
|---|---|---|
| スマホ | 傾きを読み取って送信する。担当の関節と入力の状態を表示する | 参加者のスマホのブラウザ |
| サーバー | ルームを管理し、スマホとスクリーンの間でメッセージを中継する。ランキングを保存する | Cloudflare Workers と Durable Objects |
| スクリーン | 物理演算と描画を行う。QR コード・タイム・ランキングを表示する | 会場のスクリーンに接続した PC のブラウザ |

- 物理演算はスクリーンだけで行う。全員が同じ画面を見るので、シミュレーションは1か所で足りる。サーバーはメッセージを中継するだけで、ゲームの状態を計算しない

## 技術スタック

| 領域 | 採用 | 理由 | 見送った案 |
|---|---|---|---|
| リアルタイム通信 | WebSocket。あとから WebRTC DataChannel を追加する | WebSocket はどの回線でも接続できる。WebRTC は低遅延だが、回線によっては P2P で接続できない | WebRTC のみ（当日接続できないリスクがある） |
| バックエンド | Hono、Durable Objects | Hono は Cloudflare Workers で広く使われ、ルーティングを短く書ける。Durable Objects はルームごとに1つのインスタンスで WebSocket を保持できる | Node.js のサーバー（無料のホスティングはスリープする） |
| 物理エンジン | Rapier 2D | 関節のモーターに目標角度を直接指定できる。同じ入力から同じ結果になるビルドがある | Planck.js（目標角度の制御を自作する）、Matter.js（関節のモーターが無い） |
| 描画ライブラリ | PixiJS | スプライトとフィルタがある。物理エンジンを自由に選べる | Canvas 2D（演出をすべて自作する）、Phaser（付属の物理エンジンが前提になる） |
| ゲームエンジン | 不採用 | チームに経験が無い。コードだけで開発でき、差分をレビューしやすい | Godot、Unity |
| フロントエンド | React、Vite+ | チームに React の経験がある。Cloudflare の公式ガイドがある | フレームワークなし、Svelte 5 |
| 言語 | TypeScript | クライアントとサーバーで型定義を共有できる | |
| メッセージの検証 | Valibot | 型定義と実行時の検証を1か所に書ける。使う関数だけがバンドルに入り、小さい | Zod、ArkType、TypeBox、typia、Yup、superstruct、io-ts、導入しない（[メッセージの検証](#メッセージの検証)） |
| ホスティング | Cloudflare Workers | 静的アセットと API を同じ Worker にデプロイできる。HTTPS が標準で付き、無料枠で足りる | |
| 環境とデプロイ | ローカル・プレビュー・本番の3つ。GitHub Actions が、PR ごとにプレビューを作り、`main` へのマージで本番にデプロイする | PR ごとに別の URL と別の Durable Objects のストレージができ、並行して開発してもぶつからない。デプロイの定義がリポジトリに入り、PR でレビューできる | Cloudflare の GitHub App、本番を手動でデプロイする、プレビューを作らない、共有のステージングを1つ持つ（[環境とデプロイ](#環境とデプロイ)） |
| CLI | `cf` | `wrangler` の後継。公開ベータなので、未対応の操作は `wrangler` を使う | |

### リアルタイム通信

- 先に WebSocket だけでロビーから結果までを動かす。そのあとで WebRTC DataChannel を追加する
- WebRTC に移すのは到達保証が不要なメッセージだけ（[API](api.md)）。WebRTC で接続できないときは WebSocket にフォールバックする
- WebRTC を追加する時間が無ければ WebSocket だけにする

### フロントエンド

- React が担当するのは UI（ロビー・タイム・結果・ランキングと、スマホのボタン）だけ。フレームごとの描画と通信は React の外に置く

### 環境とデプロイ

- プレビューは、Cloudflare の Workers Previews を使う。PR ごとに HTTPS の URL ができるので、傾きの読み取りをスマホの実機で検証できる
- プレビューと本番は、Durable Objects のストレージが分かれる。ルームとランキングのデータは混ざらない
- 本番で問題が出たときは、前のバージョンにロールバックする
- デプロイの決まりと上限は、[Cloudflare の注意点](cloudflare.md) に書く

| 見送った案 | 理由 |
|---|---|
| Cloudflare の GitHub App | デプロイの設定が Cloudflare のダッシュボードに入り、リポジトリからは見えない。リポジトリの所有者が Cloudflare のアカウントに入って連携する必要がある |
| 本番を手動でデプロイする | レビューと CI を経由せず、コミットしていない変更も本番に出る |
| プレビューを作らない | レビューする人が自分で動かす必要があり、スマホ4台での確認がしにくい |
| 共有のステージングを1つ持つ | 2人が同時に試すと上書きし合う |
| Version URLs（以前の Preview URLs） | Durable Objects を使う Worker では作られない |

### メッセージの検証

- メッセージの形を Valibot のスキーマで `src/shared/` に書き、TypeScript の型もスキーマから作る。スマホ・サーバー・スクリーンは同じスキーマで検証する
- `tilt` は毎秒30回届くが、どのライブラリでも検証の時間は問題にならない
- ページには React などが入るので、バンドルサイズの差は小さい。小さい差でも積み重ねると効くと考えて、小さいほうを選んだ

| 見送った案 | 理由 |
|---|---|
| Zod | 資料が最も多く、書き方は Valibot とほぼ同じ。Valibot よりバンドルが大きい |
| ArkType | 型を文字列で書くので、打ち間違いに気づきにくい。資料が少なく、バンドルが大きめ |
| TypeBox | JSON Schema の形で持てるが、今回は JSON Schema を使う場面が無い |
| typia | TypeScript の型から検証のコードを作るため、ビルドのプラグインが要る。Vite+ と Cloudflare の Vite プラグインで動くかを確かめる時間が無い |
| Yup | フォームの入力チェック向けで、`type` での振り分けが書きにくい |
| superstruct | 更新が少なく、今から選ぶ理由が無い |
| io-ts | 開発がほぼ止まっている。fp-ts が要り、関数型プログラミングの知識が前提になる |
| 導入しない | メッセージが9種類あり、手で検証を書くと漏れやすい |

### ルームと接続の片付け

- 切れた接続は、ハートビートが届かなくなったことで見分ける。スマホとスクリーンが5秒ごとに送り、最後に届いてから15秒たつとサーバーが閉じる。1回落ちただけでは閉じない
- 誰も接続していないルームは、10分後に消す。ルームコードと `phase` も一緒に消える
- プレイ中にスクリーンが切れても、サーバーは `phase` を変えない。ルームを消すときに一緒に消える
- 仕様は [API](api.md) の「heartbeat」と「ルームの削除」にある

| 見送った案 | 理由 |
|---|---|
| 切断を見分けない（WebSocket の close に任せる） | 画面のロックや電波切れでは close が届かない。関節を持ったまま残り、次の人が参加できない |
| `tilt` が途絶えたことで見分ける | スマホの追加の実装は要らないが、ロビーで `tilt` を送らない作りにすると、待っているだけで切られる |
| サーバーから ping を送り、返事で見分ける | 送るたびに Durable Object が起き、リクエストとして数える。ハートビートはランタイムが自動で返すので、ハートビートのたびには Durable Object が起きない |
| WebSocket のプロトコルの ping フレーム | ブラウザの JavaScript から送れない |
| ルームを全員が抜けて1時間後に消す | スクリーンの開き直しや一時的な切断には10分で足りる。長いほど、使われないルームが残る |
| ルームを消さない | ルームコードは約92万通りあり、ハッカソンの規模なら重ならない。ただし、使われないデータが残り続ける |
| スクリーンが切れたら、サーバーが `phase` を `lobby` に戻す | 同じルームをすぐ使い直せるが、「状態はスクリーンが決める」方針から外れる。スクリーンを開き直すと新しいルームを作るので、古いルームは消えるまで放っておけばよい |

### つなぎ直し

- 切れたら、スマホもスクリーンも同じルームに自動でつなぎ直す。スクリーンのページを開き直したときは、新しいルームを作る
- スマホは ID を接続の URL に付ける。サーバーは、切れたスマホの関節を60秒予約し、同じ ID のスマホが戻ってきたら同じ関節を渡す
- サーバーが古い接続を閉じる前に同じ ID でつないできたら、古い接続を閉じて置き換える。プレイ中なら、プレイが続く
- 通信は WebSocket のまま。WebRTC は遅延を測ってから考える。WebRTC の接続も切れるので、どちらにしても、つなぎ直しが土台になる
- サーバーの仕様は [API](api.md) の「スマホの ID と関節の予約」にある。決めた経緯は Issue #42 にある

| 見送った案 | 理由 |
|---|---|
| つなぎ直さない（ページを開き直す運用） | 作る量はゼロだが、Wi-Fi が一瞬切れただけで、4人が QR コードを読み直すことになる |
| 空いている関節に入り直す（予約しない） | サーバーは今のままでよいが、一瞬切れただけで担当が入れ替わる。結果の画面からやり直すとき、「同じ4人・同じ担当」でなくなる |
| プレイを再開する（ロビーに戻さない） | 遊んでいる人はいちばん困らないが、`docs/game.md` の「切断したらロビーに戻る」を変えることになる。待っているあいだのおじさんの扱いも決める必要がある |
| 今から WebRTC・WebTransport にする | 遅延は減るかもしれないが、つなぎ直しは要らなくならない。WebRTC は会場の回線によっては直接つながらず、WebTransport は Cloudflare Workers が受け手になれないと考えている |
| 30秒で諦める | 状態は単純だが、30秒より長い切断では戻れない。秒数の根拠が弱い。サーバーが「戻れない」と返したときだけ諦めれば、秒数を決めなくてよい |

### ログ

- Workers Logs の呼び出しのログ（リクエストやメッセージ1件ごとに自動で残るもの）は切る（`cloudflare.config.ts` の `observability.logs.invocationLogs: false`。wrangler の設定では `invocation_logs`）
- サーバーは、出来事だけを `console.log` で書く。ルームの作成と削除、接続（役割・関節・スマホの ID が付いていたか・関節を取り戻したか）、スクリーンとスマホの置き換え、切れたスマホの関節の予約、断った理由、切断（close コード）、15秒で閉じた接続、エラー、受け取った `phase`、ランキングへの保存（モード・タイム・順位。チーム名は書かない）。項目で絞り込めるように、`{ roomCode, event, ... }` のオブジェクトで書く（ランキングのログはルームに属さないので `roomCode` を持たない）
- `tilt` と `pong` の中継ではログを書かない
- スマホの ID そのものは書かない。付いていたか（`hasClientId`）と、予約か置き換えで関節を取り戻したか（`returning`）だけを書く
- 発表の日は、`npx cf observability tail --worker funyaoji` を手元で流しておき、リクエストの様子はそれで見る
- 上限の数字は [Cloudflare の注意点](cloudflare.md) の「上限」にある

| 見送った案 | 理由 |
|---|---|
| 何も変えない | スマホ4台が `tilt` を送ると、約28分で1日の上限に届く。区切りは日本時間の朝 9 時なので、リハーサルと発表の合計で28分しか持たない。ほとんどが `tilt` のログで、知りたいログが埋もれる |
| サンプリング（`head_sampling_rate`） | 設定1行で済むが、切断・断った理由・例外も同じ割合で欠ける。1% なら約46時間持つが、いちばん知りたいログの 99% が残らない |
| ログを止める（`enabled: false`） | 例外も残らず、あとから調べられない |
| Logpush・Tail Workers で外に送る | 有料プランでしか使えない |
| Analytics Engine に書く | 数や遅延の集計には向くが、出来事の記録には向かない。読むのに API トークンが要る |
| Durable Objects のストレージに自分で書く | 書き込みも Durable Objects の1日の上限を使う。読むための API も要る |
| スクリーンのブラウザに残す | サーバーの中で起きたこと（4002 で閉じた、断ったなど）が分からない |

### 遅延の計測

- スクリーンは、つながっている関節ごとに1秒に1回 `ping` を送る。増えるのは4台で毎秒4往復で、`tilt` の約7%。`pong` の中継ではログを書かない
- スマホの `pong` は、共通のクライアント（`src/net/client.ts` の `connectPhone`）が受け取ってすぐ返す。スマホのページは何もしなくてよい
- スクリーンには、関節ごとに片道の遅延（往復時間の半分）の最新の値と、直近10回の中央値を並べる。中央値は外れ値に強く「ふだんの遅延」になり、最新の値と並べると「今だけ悪い」のか「ずっと悪い」のかが分かる
- 関節が `room` から抜けたら、その関節の値を忘れる。つなぎ直したら、値も、返事を待っている `ping` も全部忘れる。5秒たっても `pong` が返らない `ping` も忘れ、5秒より遅れて届いた `pong` は使わない
- つながっていないあいだは、値を出さない
- 返事の来ない `ping` が2つ続いた関節は、値の代わりに「応答なし」と出す（確かめるための画面だけ）。最後に返った値を出し続けると、いちばん悪い「返ってこない」状態が見えないため。通信の部分（`src/net/latency.ts`）は、続けて返事が来なかった数（`missed`）を渡すだけで、どう見せるかは画面が決める
- 計測は `src/net/latency.ts` で、React の外に置く。React は表示だけをする
- `ping`・`pong` で測れるのは、ほぼ通信（スマホ → サーバー → スクリーン）の部分。ただし、両端のメインスレッドの待ち（スマホのページの処理、スクリーンの物理演算・描画）も値に入る。スクリーンの処理が重いと、値は通信より大きくなる。体感の遅延（傾けてから棒が動くまで）は、センサーの読み取り・`tilt` の送信間隔・描画の待ちが加わり、「表示される値 ＋ 約30〜60ms」が目安
- スマホとスクリーンの時計はずれているので、片道は直接は測れない。往復をスクリーンの時計だけで測り、半分にする
- 測った値は、WebRTC を足すかどうかの判断に使う。決めた経緯は Issue #24 にある

| 見送った案 | 理由 |
|---|---|
| 関節ごとに5秒に1回 | メッセージはほとんど増えないが、中央値に10回ためるのに50秒かかり、一瞬の悪化を見逃す |
| 毎秒10回など、多く送る | 往復の数が `tilt` に近づき、Durable Objects の1日の上限を目に見えて使う。表示用にそこまで細かい値は要らない |
| ボタンを押したときだけ測る | 遊んでいる最中の遅延が見えない。発表中に押す人がいない |
| 最新の値だけを出す | 遅延は毎回ぶれ、数字がチカチカして、ふだんどのくらいかが読み取れない |
| 平均を出す | たまに来る大きな値に引っぱられ、ふだんより悪く見える |
| グラフにする | 作る量が増える。見た目はフロントエンドの担当と相談が要る |
| スマホのページ（#43）が `pong` を返す | #43 の作業が増え、返し忘れると測れない。ページの処理の重さが、自動で返すより値に混ざりやすい（自動で返しても、同じメインスレッドで動くので無くなりはしない） |
| `tilt` に送った時刻を付け、`tilt` 1件ごとの遅延を出す | `tilt` の形（API）が変わる。今は通信の遅延が分かれば足りる。体感の遅延を全部測るのも、同じく API が変わる |
| 遅延を実況のテロップとして画面に出す | 見た目の話なので、フロントエンドの担当と相談してから |

### ランキング

- 保存先は、ランキング用の Durable Object を全体で1つ（SQLite のストレージ）。ルームと同じく `ctx.exports` で呼ぶので、プレビューと本番でデータが分かれる。プレビューのデータは、PR を閉じると消える
- 送るのはスクリーン。ゴールしたときに、モード・チーム名・タイム（ミリ秒）を `POST /api/rankings` で送る。日時はサーバーが付ける。状態はスクリーンが決める、の方針に合わせる
- チーム名を付ける。NFKC で正規化し（全角の英数字と空白を半角にそろえる）、前後の空白を除いて、1〜10文字。絵文字や濁点の付いた文字も1文字と数える（書記素）。改行・タブなどの制御文字と、文字の向きを変える文字や幅のない空白などの書式の文字（`Cf`。絵文字をつなぐ ZWJ は除く）は使えない。空白と見えない文字（ZWJ や異体字セレクタなど）だけの名前も断る。見えない文字だけの名前で、空に見える行ができないようにするため。孤立したサロゲートを含むものも断る。10文字は、スクリーンのランキングの1行に収まり、日本語のチーム名なら足りる長さとして決めた
- タイムは整数のミリ秒に丸め、1ミリ秒〜1時間を受け付ける。制限時間は設けない（Issue #81）ので、1時間は明らかにおかしな値を断るためだけの上限
- 上位は10件返す。同じタイムは、先に保存したほうを上にする。順位は並べた順の番号
- モードごとに1,000件まで残し、超えたら遅いものから消す。順位を数えるときに読む行の数が、送られた数に比例して増え続けないようにするため。ハッカソンの間に1,000件には届かない
- 値の形と範囲だけを確かめる。公開 URL なので誰でも送れるが、本気の不正（でたらめに速いタイムを送るなど）は防がない
- `POST /api/rankings` も、`POST /api/rooms` と同じく大量に呼ばれうる。ルームを作る API の対策（Issue #66）を、同じように Hono のミドルウェアとして前に足せる形にしてある。検査で断るものは Durable Object を呼ばないので、上限を使わない
- 仕様は [API](api.md) の「POST /api/rankings」「GET /api/rankings」に、上限への影響は [Cloudflare の注意点](cloudflare.md) にある

| 見送った案 | 理由 |
|---|---|
| D1 | SQL で書けるが、`env` のバインディングで使うので、プレビューが本番のデータベースを使わないようにする設定が別に要る。Durable Objects は、今の作りのままプレビューごとに分かれる |
| KV | 書き込みが無料プランで1日1,000回と少ない。並べ替えができず、上位を出すには全件を読んで並べることになる。書き込みがほかの場所に届くまで時間がかかる |
| ルームの Durable Object に保存する | ルームは誰もいなくなって10分で消える。ルームをまたいだランキングにならない |
| 悪い言葉を判定する | 言葉の一覧を用意して保守する手間がかかる。チーム名は会場のスクリーンの PC で入れるので、その場の人の目がある |
| 署名や合言葉で、スクリーンからの送信だと確かめる | スクリーンのページは公開されていて、鍵をページに入れると見れば分かる。ハッカソンの間は、値の範囲の確認で足りる |
| サーバーがタイムを測る | サーバーは物理演算をせず、ゴールの時刻を知らない。スクリーンの物理の時間ともずれる |
| 同じタイムを同じ順位にする | ミリ秒まで同じになることはまれで、並べた順の番号のほうが単純 |
| 件数を消さない | 送られた数だけ、順位を数えるときに読む行が増え、SQLite の読み込みの上限を使う |
| `POST` は順位だけを返し、上位は `GET` で取り直す | 結果の画面を出すたびにリクエストが1回増える |

### ルームを作る API の乱用

`POST /api/rooms` は誰でも呼べて、呼ぶたびに Durable Object を使う。守りたいのは「Durable Objects の1日の上限を、知らない人の連打で使い切られないこと」と「発表の日のデモを止めないこと」。2つの層で絞る。

- 同じ IP からの連打は、Workers の Rate Limiting（`cloudflare.config.ts` の `ROOM_RATE_LIMIT`）で、1分に10回までにする。超えたら Durable Object を呼ばずに断る
- 1日の総量は、門番の Durable Object（`RoomGate`。Worker 全体で1つ）が数え、1日に200ルームまでにする。日付は UTC で区切る（日本時間の朝9時。Cloudflare の上限が戻る時刻と同じ）
- 門番が「今日はもう作れない」と答えたら、その isolate はその応答を覚え、朝9時まで門番を呼ばずに断る。断るたびに Durable Object のリクエストを使わない（応答を覚える前に、1日の上限の確認に進んだリクエストは、それぞれ門番を呼ぶ）
- 断るときは 429 と理由（`too-many-requests`・`daily-limit`）を返し、スクリーンが理由に合った文を出す。仕様は [API](api.md) の「POST /api/rooms」、上限の数の根拠は [Cloudflare の注意点](cloudflare.md) の「ルームを作る回数の上限」にある
- 1分に10回は、会場の Wi-Fi で全員が同じ IP になっても、スクリーンを開き直すくらいでは当たらない数。ルームを作るのはスクリーンだけで、スマホは作らない
- Rate Limiting は Cloudflare のロケーションごとに数え、すぐには揃わない（[Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)）。プレビューで試すと、1つの接続で続けて呼んだときは11回目から断ったが、呼ぶたびに接続を張り直すと、2分で約40回通った。厳密でなくてよい連打よけに使い、総量は門番で厳密に数える
- 本番とプレビューは、門番のストレージが別なので、別に数える。Rate Limiting の数は、同じ `namespace` を使うので、本番とプレビューで共有する

残る穴：

- Worker の呼び出しそのもの（1日 100,000 回）は守れない。断るのも Worker の中なので、断った呼び出しも数に入る。守るには、Worker の手前で止める（下の「WAF の Rate Limiting ルール」）
- ルームコードの形をした `GET /api/rooms/<コード>/ws` は、ルームが無くても Durable Object を1回使う。この Issue の範囲の外にする
- たくさんの IP から呼ばれると、1分に10回の層は効かない。それでも門番で1日200ルームに止まる

| 見送った案 | 理由 |
|---|---|
| Turnstile（ボットの判定） | ダッシュボードでウィジェットと秘密鍵を作る手作業が要る。スクリーンのページにウィジェットを置き、サーバーで検証する作業も増える。総量は門番で止まるので、足して防げるのは「たくさんの IP から、その日の200ルームを使い切られること」だけ。そうなったときに、入れるかを決める |
| WAF の Rate Limiting ルール | Worker の手前で止められ、Worker の呼び出しも使わない。ダッシュボードで作る手作業が要り、設定がリポジトリに入らない。`workers.dev` のドメインに使えるかも確かめていない |
| 合言葉（ヘッダーの共有の秘密） | スクリーンのページは公開されていて、ページの JavaScript に書いた秘密は誰でも読める。秘密を手で入れる運用は、当日の手順を増やす |
| 門番だけ（IP ごとの層を置かない） | 1人の連打で、その日の200ルームを数分で使い切られ、デモが止まる |
| IP ごとの層だけ（門番を置かない） | IP を変えながら呼ばれると、総量に上限が無い。Rate Limiting はロケーションごとで厳密でない |
| 門番を Room のクラスに同居させる（`/api/ping` と同じく名前で分ける） | クラスは増えないが、ルームの処理と関係ない数え方が Room に混ざる |
| 1日の上限をもっと大きくする（例：1,000） | 1ルームを作るだけなら約3回なので、1,000でも約3%しか使わない。ただ、遊べるのは1日に約115回で、200を超えて作る正当な使い方が無い。小さいほうが、上限に届いたことに早く気づける |

## ディレクトリ構成

```
src/
  shared/   メッセージの型定義と、共通の定数
  server/   サーバー（Hono のルーティングと、ルーム・ランキングの Durable Objects）
  net/      通信のクライアント（WebSocket の接続と再接続。WebRTC はここに追加する）
  phone/    スマホのページ（傾きの読み取りと、UI）
  screen/
    game/   物理演算と描画。React と通信に依存しない
    ui/     スクリーンの UI（React）
docs/       ドキュメント
```

- パッケージは1つにする。設定が1つで済み、`shared/` を import するだけで型定義を共有できる
- `screen/game/` の入力は関節ごとの目標角度、出力は距離・ゴール・転倒のイベントにする。入力元がキーボードでもスマホでも同じインターフェースになり、物理演算と通信を並行して開発できる

| ディレクトリ | 担当 |
|---|---|
| `server/` | バックエンドの担当 |
| `net/`、`phone/` の傾きの読み取り | 通信の担当 |
| `screen/game/` | フロントエンドのリード |
| `screen/ui/`、`phone/` の UI | 未定 |
| `shared/` | 全員。変更は PR でレビューを受ける |
