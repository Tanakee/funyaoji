# Cloudflare の注意点

## 参照先

| 項目 | 参照先 |
|---|---|
| Worker の設定 | `cloudflare.config.ts` |
| デプロイの手順 | `.github/workflows/deploy.yml` |
| アカウント・メンバー・使用量 | Cloudflare のダッシュボード（アカウントは `team-sweater`） |
| `cf` のコマンド | [Develop, build, and deploy](https://developers.cloudflare.com/cf/projects/) |
| バージョンを戻す手順 | [Rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/) |
| 上限 | [Workers](https://developers.cloudflare.com/workers/platform/limits/)、[Durable Objects](https://developers.cloudflare.com/durable-objects/platform/pricing/)、[ログ](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)、[Previews](https://developers.cloudflare.com/workers/previews/) |

## デプロイ

- デプロイは GitHub Actions が行う（`.github/workflows/deploy.yml`）。PR ごとにプレビューを作り、`main` にマージされ、`main` の CI が通ると本番にデプロイする（`workflow_run`）
- PR を閉じる（マージする）と、そのプレビューを消し、PR のプレビューのコメントを書き換える（`cleanup` のジョブ）。そのプレビューの Durable Objects のデータも消える。同じブランチの PR がまだ開いているときは消さない。閉じたあとに確かめ直したいときは、PR を開き直すと、プレビューがまた作られる
- プレビューの名前はブランチ名（`/` を含んだまま）。URL では `/` が `-` に置き換わる
- ローカルからのデプロイ（`npx cf deploy`）は、GitHub Actions が使えないときだけ行う。レビューと CI を通らず、コミットしていない変更も本番に出る
- ローカルからデプロイすると、本番の内容が `main` とずれる。同じ変更を、あとで `main` に入れる
- 本番で問題が起きたときは、前のバージョンに戻す（[Rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)）

## アカウントのロール

- メンバーは、読み取り専用のロール（Workers Platform (Read-only)）で招待する。ログと使用量を見られる
- ローカルからのデプロイと、バージョンを戻す操作ができるのは、Super Administrator と Workers Platform Admin のロール。この2つのロールを持つ人を、2人以上にしておく
- 誰がどのロールかは、ダッシュボードの Members のページで確かめる

## 上限

無料プランを使っている。上限は1日ごとで、本番とプレビューの合計で数える。超えると、その種類の操作がエラーになる。ローカル（`npm run dev`）は数に入らない。

- ログ（Workers Logs）は1日 200,000 件まで、保存は3日。呼び出しのログを切っているので、`tilt` などのメッセージではログが残らない。残るのは、サーバーが `console.log` で書いた出来事と例外だけで、1回のプレイで数十件になる（理由は [設計](design.md) の「ログ」）
- 呼び出しのログを戻すと、受信したメッセージ1通ごとに1件記録され、スマホ4台が `tilt` を送り続けると約28分で上限に届く。ログを減らしても、Durable Objects のリクエストの上限（下の「Durable Objects の上限と、1日に遊べる回数」）は変わらない
- 1日の区切りは UTC の 0 時（日本時間の朝 9 時）。前日の夜に開発で使った分と、当日の朝 9 時より前に使った分は、同じ日に数える。朝 9 時を過ぎて使った分から、次の日に数える

### Durable Objects の上限と、1日に遊べる回数

2026年11月時点の無料プランの上限（[Durable Objects: Pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)）。

| 項目 | 1日の上限 | 数え方 |
|---|---|---|
| リクエスト | 100,000 回 | HTTP のリクエスト・RPC・アラームは1回ずつ。WebSocket の接続を開くのも1回。WebSocket で受信したメッセージは 20 通で1回 |
| 起きている時間（Duration） | 13,000 GB-s | 起きているあいだの時間 × 128 MB。休止（Hibernation）しているあいだは数えない |
| SQLite の書き込み | 100,000 行 | 書き込んだ行の数。`setAlarm()` は1回で1行 |
| SQLite の読み込み | 5,000,000 行 | 読み込んだ行の数 |

- 送信したメッセージ（サーバーからの中継）と、WebSocket のプロトコルの ping は数えない
- SQLite の行は、1回のプレイで数十行（ルームの状態とアラーム）なので、上限には届かない
- ランキング（[設計](design.md) の「ランキング」）は、保存（`POST /api/rankings`）と取得（`GET /api/rankings`）がそれぞれリクエスト1回（RPC）。保存は、書き込みが2行（行と索引。1,000件を超えて消すときはさらに2行）、読み込みが最大で約2,000行（順位を数えるのと、1,000件を超えたものを探すので、そのモードの行を読む）。取得は、読み込みが約10行。読み込みの上限からは、保存は1日に少なくとも約2,500回でき、リクエストの上限より先には届かない
- ハートビートは、ランタイムが自動で返す（`setWebSocketAutoResponse`）ので、起きている時間には入らない。リクエストに入るかは、ドキュメントに書かれていない。下の計算では、入るものとして数える（入らなくても、ほとんど変わらない）

#### 1分あたりのリクエスト

スマホ4台とスクリーン1台。サーバーが受信するメッセージを数える。

| メッセージ | 毎秒の受信 | ロビー | プレイ中 |
|---|---|---|---|
| `tilt`（4台 × 毎秒30回） | 120 | なし | あり |
| `ping`（スクリーン → 4関節に1秒に1回） | 4 | あり | あり |
| `pong`（4台が1秒に1回） | 4 | あり | あり |
| `heartbeat`（5接続が5秒に1回） | 1 | あり | あり |

- ロビー：毎秒9通 → 1分に540通 ÷ 20 = 27回。アラーム（切れた接続を調べる）を足して、**約32回/分**。アラームは、最後にメッセージが届いた時刻から数えるので、毎秒 `ping`・`pong` が届くあいだは約14〜15秒に1回（約4回/分）になる。ここでは多めに5回/分と数える（ハートビートしか届かないときの10〜15秒に1回に合わせた）
- プレイ中：毎秒129通 → 1分に7,740通 ÷ 20 = 387回。アラームを足して、**約392回/分**。ほとんどが `tilt`
- `status`（スクリーン → スマホ）は、送る間隔がまだ決まっていないので入れていない。毎秒10回なら、1分に30回増える

#### 1回のプレイ

ロビーで2分待ち、120秒（タイムアウト）遊び、結果を30秒見る、とする。結果の画面はロビーと同じ数とする。

| 内訳 | リクエスト |
|---|---|
| 門番に聞く（RPC）、ルームを作る（RPC）、5台が接続する、ルームを消すアラーム | 約8 |
| ランキングの保存と取得（ゴールしたときだけ） | 約2 |
| ロビー 2分 × 32 | 64 |
| プレイ中 2分 × 392 | 784 |
| 結果 0.5分 × 32 | 16 |
| 合計 | **約870** |

- 1日に遊べる回数：100,000 ÷ 870 ≒ **約115回**。リハーサルと発表、本番とプレビューの合計
- 遊び続けられる時間：100,000 ÷ 392 ≒ 255分 ≒ **約4.3時間**（プレイ中だけを数えたとき）
- `tilt` をロビーでも送り続けると、1回 4.5分 × 392 ≒ 1,760 で、**約57回**に減る。ロビーで `tilt` を送るかは、まだ決まっていない。`scripts/fake-phone.ts` は、`joined` のあと、フェーズに関係なく `tilt` を送り続けるので、`fake-phone` で試すときの数はこちらに近い
- つなぎ直しで増えるのは、接続を開く1回だけ（`joined`・`room` はサーバーが送るので数えない）。切れているあいだは `tilt` が来ないので、むしろ減る

#### ルームを作る回数の上限

`POST /api/rooms` は、同じ IP から1分に10回、1日に200ルームまで（理由は [設計](design.md) の「ルームを作る API の乱用」）。

- 誰も接続しないルームを1つ作ると、門番に聞く・ルームを作る・10分後にルームを消すアラームで、約3回使う。200ルームで約600回、1日の上限の約0.6%。知らない人に上限まで作られても、遊べる回数はほとんど減らない
- 遊べるのは1日に約115回で、1つのルームで何回も遊べる。200は、リハーサルと発表でスクリーンを開き直す分を足しても届かない数
- 上限に届いたあとは、Worker の isolate ごとに、最初に断られた応答を覚え、そのあとは朝9時まで門番を呼ばずに断る。応答を覚える前に、IP ごとの回数の確認を通って1日の上限の確認に進んだリクエストは、それぞれ門番を呼ぶが、Durable Objects のリクエストはほとんど増えない
- 1分に10回で断った呼び出しは、Durable Object を使わない。Workers の呼び出し（1日 100,000 回）には入る
- 門番の数は、本番とプレビューで別。プレビューを消す（PR を閉じる）と、そのプレビューの数も消える
- 発表の日に上限（200ルーム）に届いてデモが止まりそうなときは、`src/server/room-quota.ts` の `DAILY_ROOM_LIMIT` を上げてデプロイする

#### 開発で使う分

- `scripts/fake-phone.ts` を4台でプレビューや本番につなぐと、送り続けているあいだ1時間に約22,000回使う。スクリーンもつないで `ping` を送っているときは約23,500回。どちらも1日の上限の約4分の1
- スマホがつながったままのスクリーンのタブは、1時間に約1,900回使う（`ping`・`pong` で約1,440回、ハートビートと多めに数えたアラームで約480回）。スマホがつながっていなくても、アラームで1時間に約300回使う
- どちらも、本番とプレビューの合計で数える

#### 起きている時間

- ロビーでも毎秒 `ping` が届くので、スマホがつながっているあいだ、ルームの Durable Object はずっと起きている
- 13,000 GB-s ÷ 0.125 GB ＝ 104,000秒 ≒ **約29時間**。ルームが起きている時間の合計が、1日にこれを超えると届く
- 1回のプレイ（4.5分）なら約385回分で、リクエストの上限（約115回）より先には届かない。スマホがつながったままのタブを、本番とプレビューで1日中開いておくと届く

#### 足りないときの対策

どれを取るかは決まっていない。

| 対策 | 効果 | 代わりに失うもの |
|---|---|---|
| `tilt` を毎秒15回にする | プレイ中が約210回/分になり、1日に約195回遊べる | 動きの滑らかさ。遅延が最大で約33ミリ秒増える |
| `tilt` を、角度が変わったときだけ送る | 手を止めている分だけ減る | 送らないあいだ、`status` の入力の状態が切れて見える |
| 当日は、プレビューで遊ばない・`fake-phone` をつながない | 開発で使う分が無くなる | 当日に直したものを、プレビューで確かめられない |
| 使わないスクリーンのタブを閉じる | 放っておいたルームの分が無くなる | なし |
| 有料プラン（Workers Paid、月5ドル）にする | 1日の上限が無くなる。1か月に100万回までは月額に含まれ、超えた分を払う | お金がかかる |

- 使った数は、Cloudflare のダッシュボード（Workers & Pages → Durable Objects）で見られる。Durable Objects のメトリクスは 20 通で1回にする前の実際の数なので、上の計算より大きく見えることがある（[Durable Objects: Pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) の脚注）

## データや URL に影響する変更

| 変更 | 影響 |
|---|---|
| Worker の名前（`cloudflare.config.ts` の `name`） | 別の Worker としてデプロイされる。Durable Objects のデータは引き継がれない |
| `workers.dev` のサブドメイン（ダッシュボード） | 本番とプレビューの URL が全部変わる。データは残る |
| Durable Objects のクラスを消す | そのクラスのデータが消える。クラスを足した・消したバージョンをまたいでは、前のバージョンに戻せない |
| Durable Objects を `env` のバインディングで呼ぶ | プレビューが本番のストレージを使う。`ctx.exports` で呼ぶ（[Previews: Resources and isolation](https://developers.cloudflare.com/workers/previews/resources/)） |
| プレビューを消す・PR を閉じる | そのプレビューの Durable Objects のデータも消える。PR を閉じると、GitHub Actions がプレビューを消す |
